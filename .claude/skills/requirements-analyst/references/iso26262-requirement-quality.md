# ISO 26262 기반 요구사항 품질 속성 (참고 요약)

> 주의: 이 문서는 ISO 26262(2018) Part 8, Clause 6 "Specification and management of requirements"의 널리 알려진 개념을 정리한 **참고용 요약**이며, ISO 표준 원문을 그대로 인용한 것이 아닙니다 (ISO 표준은 저작권으로 보호되어 원문 재게재가 불가). 실제 안전성 심사/인증에 사용할 때는 조직이 보유한 정식 ISO 26262-8:2018 문서의 Clause 6 원문을 반드시 대조 확인하십시오.

## 개별 요구사항이 가져야 할 6가지 속성 (Clause 6.4.1 개념)

하나의 요구사항 문장은 다음 6가지를 모두 만족해야 한다.

1. **명확함(Unambiguous)** — 해석이 하나뿐이어야 한다. 여러 이해관계자가 서로 다르게 해석할 수 있으면 안 됨.
2. **이해 가능함(Comprehensible)** — 관련 이해관계자(개발자, 테스터, 심사원 등)가 별도 설명 없이 이해할 수 있어야 함.
3. **원자적임(Atomic)** — 하나의 요구사항은 더 이상 분리할 수 없는 단일 요구사항이어야 한다. "그리고", "또는"으로 여러 요구사항을 묶지 않는다.
4. **일관됨(Consistent)** — 요구사항 자체가 스스로 모순되지 않고, 동일 문서/상위 문서의 다른 요구사항과도 모순되지 않아야 한다.
5. **실현 가능함(Feasible)** — 현재 프로젝트의 기술/일정/예산 제약 내에서 구현 가능해야 한다.
6. **검증 가능함(Verifiable)** — 산출물이 이 요구사항을 만족하는지 확인할 방법이 존재하고, 실제로 수행 가능해야 한다. "어떻게 검증할지 모르는" 요구사항은 이 속성을 위반한 것이다.

## 요구사항 집합(문서 전체)이 가져야 할 추가 속성

ISO 26262-8 및 ISO/IEC/IEEE 29148의 공통 개념을 결합한 체크리스트:

- **완전성(Complete)**: 필요한 요구사항이 빠짐없이 존재하는가 (TBD/TBC 항목이 남아있지 않은가).
- **필요성(Necessary)**: 상위 요구사항/이해관계자 요구를 만족시키는 데 실제로 필요한 요구사항인가 (불필요한 "있으면 좋은" 항목은 별도 표시).
- **적합성(Correct)**: 요구사항이 실제 사용자/시스템 니즈를 정확히 반영하는가.
- **추적 가능함(Traceable)**: 상위(이해관계자/상위 요구사항)와 하위(설계, 코드, 테스트케이스) 산출물로 양방향 추적이 가능해야 한다 — 자세한 방법은 `uml-sysml-traceability.md` 참고.
- **표준 준수(Conforming)**: 조직에서 정한 요구사항 작성 규칙/템플릿을 따라야 한다.

## 요구사항 속성(메타데이터) — Clause 6.4.3 개념

각 요구사항 항목에는 최소한 다음 속성이 함께 관리되어야 한다 (본문 서술과 별도로 메타데이터로 관리):

| 속성 | 설명 |
|---|---|
| 고유 식별자(ID) | 예: `SYS-REQ-0012`, `SWE-REQ-0045`. 변경되지 않는 영구 식별자 |
| 상태(Status) | 초안(Draft) / 검토중(In Review) / 승인(Approved) / 베이스라인(Baselined) / 폐기(Obsolete) |
| 출처(Source) | 이 요구사항이 유래한 상위 요구사항 ID 또는 이해관계자 요구 |
| 안전 관련 여부 / ASIL | 해당 요구사항이 안전요구사항인지, 어떤 ASIL(QM/A/B/C/D)이 할당되는지 — **주의: 본 스킬은 상위에서 이미 확정된 ASIL/안전목표를 입력으로 받아 요구사항을 작성하는 역할이며, HARA·ASIL 결정·안전목표 도출 자체는 범위 밖이다.** ASIL이 입력되지 않았다면 임의로 부여하지 말고 사용자에게 확인한다. |
| 검증 기준/방법(Verification criteria) | 이 요구사항을 어떻게 검증할지 (테스트, 분석, 리뷰, 시뮬레이션 등) |
| 우선순위(Priority) | 선택 사항, 프로젝트 정책에 따름 |

## 요구사항 명료성(clarity)을 위한 실무 작성 패턴 — EARS

애매한 서술을 방지하기 위해 EARS(Easy Approach to Requirements Syntax) 패턴 사용을 권장한다. 대상 요구사항의 성격에 맞는 패턴을 고른다.

- **유비쿼터스(항상 성립)**: "The <system> shall <동작>."
- **이벤트 기반**: "WHEN <트리거 이벤트>, the <system> shall <동작>."
- **상태 기반**: "WHILE <상태>, the <system> shall <동작>."
- **원치 않는 동작(예외/오류) 처리**: "IF <원치 않는 조건>, THEN the <system> shall <동작>."
- **선택적 기능**: "WHERE <옵션 기능이 포함된 경우>, the <system> shall <동작>."
- **복합**: 위 키워드(WHEN/WHILE/IF/WHERE)를 조합, 단 하나의 요구사항 문장에는 하나의 "shall"만 사용 (원자성 유지).

## 모호어 금지 목록 (명확성 검증 시 자동으로 걸러낼 표현)

다음과 같은 표현이 요구사항 본문에 등장하면 "명확성 위반 후보"로 표시하고 구체적 수치/조건으로 바꾸도록 제안한다:

적절한/충분한/가능한 한/신속히/즉시(수치 없이)/일반적으로/등/기타/필요시/사용자 친화적인/최적화된/안정적인(수치 없이)/TBD/TBC/향후 결정

예: "시스템은 충분히 빠르게 응답해야 한다" (X) → "시스템은 이벤트 발생 후 100ms 이내에 응답해야 한다" (O)
