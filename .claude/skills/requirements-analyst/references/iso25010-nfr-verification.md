# ISO/IEC 25010:2023 기반 비기능 요구사항 작성 및 검증방안 가이드

> 주의: 이 문서는 ISO/IEC 25010:2023의 품질특성 구조를 공개된 2차 자료(예: iso25000.com, arc42 quality model 등)를 바탕으로 정리한 **참고용 요약**이며, ISO 표준 원문 전체를 인용한 것이 아니다. 실제 문서화 시 조직이 보유한 정식 표준 문서를 대조 확인할 것.

## 9대 품질특성과 하위특성

비기능 요구사항(NFR)을 작성할 때 반드시 아래 9개 특성 중 어디에 해당하는지 분류하고, 누락된 특성이 없는지 점검한다.

| # | 품질특성 | 하위특성 |
|---|---|---|
| 1 | 기능 적합성 (Functional Suitability) | 기능 완전성, 기능 적절성, 기능 정확성 |
| 2 | 성능 효율성 (Performance Efficiency) | 시간 반응성(Time behavior), 용량(Capacity), 자원 활용성(Resource utilization) |
| 3 | 호환성 (Compatibility) | 공존성(Co-existence), 상호운용성(Interoperability) |
| 4 | 상호작용 역량 (Interaction Capability) | 적절성 인식성, 학습성, 운용성, 사용자 오류 보호, 사용자 참여성, 포용성(Inclusivity), 사용자 지원성, 자기 기술성(Self-descriptiveness) |
| 5 | 신뢰성 (Reliability) | 결함 없음(Faultlessness), 결함 허용성(Fault tolerance), 가용성(Availability), 복구성(Recoverability) |
| 6 | 보안성 (Security) | 기밀성, 무결성, 부인방지, 책임추적성, 인증성, 저항성(Resistance) |
| 7 | 유지보수성 (Maintainability) | 모듈성, 재사용성, 분석 용이성, 수정 용이성 |
| 8 | 유연성 (Flexibility) | 시험 용이성(Testability), 적응성, 확장성(Scalability), 설치 용이성, 대체 용이성 |
| 9 | 안전성 (Safety) | 운용 제약, 위험 식별, 고장 안전(Fail-safe), 위험 경고, 안전 통합 |

> "안전성(Safety)" 특성은 ISO 26262의 기능안전 개념과 인접하지만 별개다. ISO 25010의 Safety는 제품 품질모델 관점(운용 제약, fail-safe 등)이고, ISO 26262는 전자/전기 시스템의 오작동으로 인한 위해 방지를 다루는 프로세스/기술 표준이다. 안전요구사항은 `iso26262-requirement-quality.md`의 규칙도 함께 적용한다.

## NFR 작성 템플릿 (품질특성별 공통 구조)

```
[NFR-ID] <품질특성>/<하위특성>
요구사항: <시스템은 ~해야 한다 — 반드시 정량적 기준 포함>
근거/출처: <상위 요구사항 또는 이해관계자 니즈>
검증방안: <방법 + 합格 기준 + 필요 도구/환경>
```

정량 기준이 없는 NFR(예: "빨라야 한다", "안전해야 한다")은 작성 금지 — 반드시 측정 가능한 수치, 임계값, 통과/실패 기준을 포함해야 한다.

## 하위특성별 실행 가능한 검증방안 매핑

아래 표에서 **실행 가능(검증 인프라가 일반적으로 확보 가능한 방법)**한 검증방안만 제시한다. 프로젝트의 실제 테스트 환경/툴체인이 확인되지 않은 경우, 특정 도구를 단정하지 말고 "동적 성능 측정(부하테스트 도구 필요, 가용 환경 확인 요망)"처럼 전제조건을 명시한다.

| 하위특성 예 | 실행 가능한 검증방안 | 지양할 검증방안 (실행 불가/모호) |
|---|---|---|
| 시간 반응성 | 성능 측정/벤치마크 테스트 (예: 계측기·프로파일러로 응답시간 측정 후 임계값 비교) | "충분히 빠른지 사용자가 체감" (주관적, 측정 불가) |
| 용량 | 부하테스트/스트레스테스트 (예: 동시 N 트랜잭션 처리 확인) | "필요시 확장 가능해야 한다" (조건 불명확) |
| 자원 활용성 | 정적/동적 리소스 프로파일링 (CPU/메모리/스택 사용량 측정) | "리소스를 적절히 사용해야 한다" |
| 상호운용성 | 인터페이스 규격 기반 통합시험, 프로토콜 컨포먼스 테스트 | "다른 시스템과 잘 연동되어야 한다" |
| 신뢰성(가용성) | 장시간 운영시험(soak test)으로 MTBF/가동률 측정, 결함 주입 테스트(fault injection) | "안정적으로 동작해야 한다" |
| 복구성 | 결함 주입 후 정해진 시간 내 복구 여부 측정 | "빠르게 복구되어야 한다"(시간 미명시) |
| 보안성 | 정적분석(SAST), 침투테스트, 코드 리뷰, 위협모델링 기반 시나리오 테스트 — **단, 침투테스트/취약점 점검은 반드시 사전 승인된 범위·환경에서만 수행하도록 명시** | 근거 없는 "해킹 불가능해야 한다" |
| 유지보수성 | 정적분석 지표(순환복잡도, 결합도) 측정, 코드 리뷰 체크리스트 | "유지보수가 쉬워야 한다" |
| 유연성(시험 용이성) | 테스트 커버리지 측정, 테스트 자동화 가능 여부 리뷰 | - |
| 안전성(Fail-safe) | 고장주입시험(fault injection)으로 안전상태 전이 확인, FMEA/FTA 결과 기반 분석 리뷰 | "위험을 최소화해야 한다"(기준 없음) |

## 검증방안 제시 시 필수 체크

요구사항마다 검증방안을 제시하기 전에 다음을 스스로 점검하고, 하나라도 불확실하면 사용자에게 확인 후 진행한다 (지어내지 않는다):

1. 이 검증방법을 수행할 도구/환경/데이터가 실제로 존재하거나 확보 가능한가?
2. 통과/실패를 가르는 정량적 기준이 요구사항 본문에 명시되어 있는가?
3. 검증 시점(어느 프로세스/마일스톤에서 수행되는가: SWE.4/SWE.5/SWE.6/SYS.5/VAL.1 등)이 특정되는가?
4. 파괴적이거나 프로덕션에 영향을 줄 수 있는 검증(부하테스트, 침투테스트 등)이라면, 격리된 환경에서 수행한다는 전제가 명시되어 있는가?
