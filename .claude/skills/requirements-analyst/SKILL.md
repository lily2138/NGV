# 요구사항 분석 스킬

이 스킬은 이해관계자 니즈 또는 상위 요구사항으로부터 시스템/소프트웨어 요구사항을 도출·작성·점검하는 절차를 정의한다.

## 참고자료 (필요할 때 불러오고, 통째로 대화창에 붙여넣지 말 것)

- `references/iso26262-requirement-quality.md` — 개별 요구사항 품질 속성(명확함/이해가능/원자적/일관됨/실현가능/검증가능), 요구사항 메타데이터 속성, EARS 작성 패턴, 모호어 금지 목록.
- `references/iso25010-nfr-verification.md` — ISO 25010:2023 9대 품질특성/하위특성, 비기능요구사항 작성 템플릿, 하위특성별 **실행 가능한** 검증방안과 지양할 검증방안 매핑.
- `references/uml-sysml-traceability.md` — 기능 요구사항의 drawio 기반 다이어그램 매핑, 저장소 실제 템플릿(TPL-SWE1-001/002/003, TPL-TRC-001) 구조와 산출물 명명 규칙, 요구사항 ID 체계, 추적성 매트릭스(RTM) 유지 방안.

> 위 참고자료의 ISO 26262/ISO 25010 관련 내용은 공개 2차 자료 기반의 **참고용 요약**이다 (표준 원문 그대로의 인용이 아님). 실제 심사/인증 산출물로 확정하기 전에는 조직이 보유한 정식 표준 문서로 대조 확인해야 한다는 점을 사용자에게 안내한다.

## 0. 템플릿 확보 (최우선, 생략 불가)

이 스킬로 작성하는 모든 요구사항 문서는 저장소의 실제 템플릿을 그대로 따라야 한다. `WP_Templates/`에 다음 템플릿이 있다 (2026-09-17 기준 스냅샷, 작업 시작 시 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`와 대상 파일을 다시 읽어 최신 버전인지 확인한다):

- `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-001_SW 요구사항 명세서 템플릿.docx` → 산출물 `ENG-SWE1-001_SW 요구사항 명세서.docx`
- `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-002_Use Case 명세서 템플릿.docx` → 산출물 `ENG-SWE1-002_Use Case 명세서.docx`
- `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-003_Use Case 다이어그램 템플릿.drawio` → Use Case 다이어그램 원본
- `WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx` → 산출물 `ENG-TRC-001_양방향 요구사항 추적 매트릭스.xlsx` (자세한 컬럼 구조는 `uml-sysml-traceability.md` 4절)

시스템 레벨(SYS.1/SYS.2) 전용 템플릿은 현재 `WP_Templates`에 없다 — SYS 요구사항 작업 요청 시 SWE.1 템플릿 구조를 준용할지 사용자에게 먼저 확인하고, 임의로 새 구조를 만들지 않는다.

1. docx/xlsx 템플릿은 `docx`/`xlsx` 스킬로, drawio는 텍스트 그대로 읽어 구조를 확인한다 (Bash `unzip -p`로도 확인 가능, `architecture-designer`의 `swe2-template-guide.md` 0절과 동일한 방식).
2. 위 목록에 없는 종류의 문서를 요청받으면(예: 다른 프로세스의 요구사항 양식), 지어내지 말고 등록부(`PRC-TPL-001`)에서 대응 템플릿을 찾거나 사용자에게 요청한다.
3. 템플릿의 섹션 구성, 필드명, 표/시트 형식을 임의로 바꾸지 않는다. 각 절의 "작성 안내" 문구는 실제 내용으로 교체한다. xlsx는 안내용 빈 행(보통 10행) 이전을 건드리지 않고 그 이후에 실제 데이터를 추가한다.

## 1. 요구사항 분석 절차

1. **범위 확인**: 이번 작업이 시스템 요구사항(SYS.1 요구사항 도출/SYS.2 시스템 요구사항 분석)인지, 소프트웨어 요구사항(SWE.1)인지, 안전요구사항을 포함하는지 확인한다. 안전요구사항이라면 상위에서 확정된 ASIL/안전목표를 입력으로 요구한다 — HARA나 ASIL 결정 자체는 이 스킬의 범위가 아니다.
2. **입력 수집**: 이해관계자 요구, 상위 요구사항, 기존 문서, 인터뷰/이슈 등 입력 자료를 Read/Grep/Glob으로 확인한다. 근거 없이 요구사항을 창작하지 않는다.
3. **요구사항 분류**: 각 요구사항 후보를 기능/비기능으로 분류한다.
   - **기능 요구사항**: 원자적 문장으로 서술(`iso26262-requirement-quality.md`의 EARS 패턴 사용) + `TPL-SWE1-002`(Use Case 명세서)와 `TPL-SWE1-003`(drawio Use Case 다이어그램)로 표현(`uml-sysml-traceability.md` 1절 매핑 사용).
   - **비기능 요구사항**: ISO 25010 품질특성/하위특성으로 분류 + 정량적 수치 포함 + `iso25010-nfr-verification.md` 매핑표를 참고해 **실행 가능한** 검증방안 제시. 매핑표에 없는 새로운 검증방안을 제안할 때도 반드시 "실행 가능 여부 필수 체크"(해당 파일 4절)를 통과해야 한다.
4. **품질 점검(명확성/일관성)**: 작성한 모든 요구사항에 대해 `iso26262-requirement-quality.md`의 6대 속성(명확함/이해가능/원자적/일관됨/실현가능/검증가능)과 모호어 금지 목록을 적용해 자체 검토한다. 위반 항목은 고쳐 쓰거나, 고칠 수 없으면 사용자에게 확인을 요청한다.
5. **ID 부여 및 추적성 연결**: `uml-sysml-traceability.md` 3절의 ID 체계로 신규 ID를 부여하고, `TPL-TRC-001` 기반 RTM(`ENG-TRC-001_양방향 요구사항 추적 매트릭스.xlsx`)의 `Upper Req`/`SW Req` 컬럼에 상위-하위 연결을 즉시 반영한다 (같은 작업 내에서 RTM 갱신까지 완료 — 나중으로 미루지 않는다). RTM이 아직 없으면 템플릿을 복사해 새로 만든다.
6. **일관성 교차 점검**: 새로 작성/수정한 요구사항이 동일 계층 또는 인접 계층의 기존 요구사항과 용어·단위·조건 면에서 상충하지 않는지 확인한다. 상충이 발견되면 임의로 하나를 택하지 말고 사용자에게 알린다.
7. **결과 보고**: 템플릿 형식에 맞춘 요구사항 문서(및 다이어그램 소스, RTM 갱신분)를 제시하고, 각 요구사항에 대해 (a) 분류(기능/비기능·품질특성), (b) 다이어그램 또는 검증방안, (c) 추적 ID/관계, (d) 품질 점검 결과(위반 없음 또는 남은 이슈)를 요약해 보고한다.

## 출력 시 유의사항

- 모든 요구사항 문서(docx), 다이어그램 원본(drawio), RTM(xlsx)은 `WP_Templates`에서 복사한 실제 템플릿 형식 그대로, `PRC-TPL-001` 등록부의 명명 규칙(`<산출물 ID>_<산출물명>.<확장자>`)에 맞춰 저장한다. 완성 산출물을 담을 저장소 폴더가 없으면 임의로 새로 만들지 말고 사용자에게 위치를 확인한다.
- 요구사항을 짓지 말 것: 입력 근거가 없는 요구사항은 만들지 말고, 부족한 정보는 사용자에게 질문한다.
- 이 스킬의 결과물은 공식 안전성 인증/A-SPICE 심사 판정이 아니라 초안/분석 지원임을 명시한다.
