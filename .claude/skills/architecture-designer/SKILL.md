# 아키텍처 설계 스킬

이 스킬은 소프트웨어 요구사항으로부터 소프트웨어 아키텍처(정적/동적 구조, 인터페이스, 통합 순서)를 설계하는 절차를 정의한다. 작업은 **제안 단계**와 **상세설계 단계**의 두 단계로 나뉜다.

## 참고자료 (필요할 때 불러오고, 통째로 대화창에 붙여넣지 말 것)

- `references/aspice-swe2-base-practices.md` — A-SPICE 4.1 SWE.2(소프트웨어 아키텍처 설계) 프로세스 목적/성과/기본관행(BP1~BP5) 공식 원문 발췌.
- `references/iso26262-part6-architecture-principles.md` — ISO 26262-6 아키텍처 설계 원칙(계층 구조, 응집력/결합도, 공간적 분리, 공유자원 관리), 표기법, 검증방법 참고 요약.
- `references/solid-and-architecture-styles.md` — 컴포넌트 수준 SOLID 원칙, 인터페이스 전용 통신 규칙, 응집력/결합도 점검 체크리스트, 변경 유연성 확보 기법, **아키텍처 스타일 후보 카탈로그**(제안 단계에서 사용).
- `references/swe2-template-guide.md` — 저장소 실제 템플릿(`WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001.docx`, `TPL-SWE2-002.drawio`)의 목차/도형 구조, 산출물 명명 규칙(`PRC-TPL-001` 등록부 기준), 사용자 요구사항이 어느 절에 대응하는지 매핑.

> ISO 26262/A-SPICE 관련 내용 중 A-SPICE 부분은 VDA QMC 공개 프리뷰 원문 발췌이고, ISO 26262 부분은 공개 2차 자료 기반 참고 요약이다(표준 원문 직접 인용 아님). 실제 인증/심사 산출물로 확정하기 전 정식 표준 문서 대조가 필요함을 사용자에게 안내한다.

## 0. 사전 확인 (매번 수행)

1. `references/swe2-template-guide.md` 0절의 절차대로 실제 템플릿 파일(`WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`, `TPL-SWE2-001*.docx`, `TPL-SWE2-002*.drawio`)을 다시 확인한다. 캐시된 참고자료와 실제 파일이 다르면 실제 파일을 따른다.
2. 입력 소프트웨어 요구사항(SWE.1 산출물, `requirements-analyst` 스킬이 만든 RTM 등)의 위치를 Read/Grep/Glob으로 확인한다. 요구사항 없이 아키텍처를 창작하지 않는다 — 못 찾으면 사용자에게 위치를 확인한다.
3. 시스템 특성(실시간성 요구, ASIL/안전무결성 수준, 예상 변경/확장 빈도, 재사용 가능한 플랫폼(AUTOSAR 등) 여부)이 입력에 없으면, 스타일 후보를 좁히기 위해 필요한 최소한만 사용자에게 질문한다(전부 지어내지 않는다).

## 1. 제안 단계 (사용자가 선택하기 전까지 상세설계로 넘어가지 않는다)

1. `references/solid-and-architecture-styles.md` 5절의 스타일 카탈로그에서 시스템 특성에 맞는 **2~3개 후보**를 고른다 (복합 적용 후보 포함 가능).
2. 각 후보에 대해: 개요, 이 프로젝트에 적용했을 때의 강점/약점, 응집력·결합도·변경유연성·SOLID 관점에서의 평가를 요약한 비교표를 작성한다.
3. **이 에이전트는 사용자와 직접 대화할 수 없다(비대화형으로 실행됨).** 상세설계서 작성을 진행하지 말고, 비교표와 각 후보의 권장 상황을 결과로 반환해 호출자가 사용자의 선택을 받은 뒤 다시 요청하도록 안내 문구를 포함한다.
4. 사용자가 이미 특정 스타일을 지정했거나 이전 대화에서 후보를 선택한 것이 명확한 경우에만 2단계로 바로 진행한다.

## 2. 상세설계 단계 (사용자가 후보를 선택한 이후)

1. `references/swe2-template-guide.md` 2절의 목차 구조를 **그대로** 따라 TPL-SWE2-001 산출물을 작성한다. 각 절의 "작성 안내" 문구는 실제 내용으로 교체한다.
2. 정적 구조(3장·5장·6장)를 작성하며 다음을 강제한다:
   - 모든 컴포넌트 간 연결은 6장에 정의된 인터페이스를 통해서만 존재해야 한다 (`solid-and-architecture-styles.md` 2절 규칙). 인터페이스 없는 직접 참조를 발견하면 인터페이스를 신설해 재구성한다.
   - 4장(컴포넌트 책임) 작성 시 `solid-and-architecture-styles.md` 3절 체크리스트로 각 컴포넌트의 응집력을, 5장 작성 시 결합도를 점검한다. 걸리는 항목이 있으면 컴포넌트 경계를 재검토하고 그 근거를 남긴다.
   - 2장(아키텍처 설계 원칙)에 SOLID 5원칙을 이 아키텍처에 어떻게 적용했는지 구체적으로 서술한다 (원칙명만 나열하지 않는다).
3. 동적 동작(7장·8장)을 TPL-SWE2-002(drawio)와 함께 작성한다 — drawio 작성 규칙은 `swe2-template-guide.md` 3절을 따른다.
4. 11장(통합 전략)에서 컴포넌트 통합 순서를 정의한다: 5장의 정적 의존성 그래프를 위상 정렬(topological sort)해 하위 의존 컴포넌트부터 통합하는 것을 기본으로 하되, 안전 등급이 높거나 리스크가 큰 컴포넌트를 우선 검증해야 하는 경우 그 근거와 함께 순서를 조정한다. 아직 구현되지 않은 컴포넌트를 먼저 통합해야 하면 필요한 스텁/드라이버를 명시한다.
5. 12장·14장에서 요구사항 할당과 추적성을 확립한다 — 소프트웨어 요구사항 ID(→ `requirements-analyst`가 부여한 `SWE-REQ-*`) 각각을 이 아키텍처의 요소/인터페이스 ID에 매핑하고, 누락되거나 두 곳 이상에 중복 할당된 요구사항이 없는지 확인한다. `requirements-analyst`가 관리하는 추적성 매트릭스(RTM)가 있다면 같은 작업 내에서 아키텍처 요소 컬럼을 갱신한다.
6. 9장(오류 격리와 안전 동작)·13장(자원 및 배포 경계)에서 ISO 26262-6의 공간적 분리·공유자원 관리 원칙(`iso26262-part6-architecture-principles.md`)을 반영한다. ASIL 정보가 입력되지 않았다면 임의로 부여하지 말고 사용자에게 확인한다.
7. 10장(품질속성 분석)에서 성능/신뢰성/유지보수성 등 주요 품질속성 시나리오와 이 아키텍처의 대응을 분석하고, 실제 수행 가능한 검증방법(`iso26262-part6-architecture-principles.md`의 검증방법 목록 참고)을 제시한다.
8. 15장에 입력 요구사항, 적용 표준(A-SPICE 4.1, ISO 26262-6), 참고한 다이어그램 원본 경로, 설계 결정 기록을 남긴다.

## 3. 출력 및 저장

- 완성한 문서/다이어그램의 저장 위치와 파일명은 `swe2-template-guide.md` 1절의 명명 규칙(`ENG-SWE2-001_...`, `ENG-SWE2-002_...`)을 따른다. 저장소에 완성 산출물 폴더가 없으면 임의로 새 폴더를 만들지 말고 사용자에게 위치를 확인한다.
- 산출물을 지어내지 않는다 — 입력 요구사항이나 사용자 확인 없이 컴포넌트/인터페이스를 창작하지 말고, 불확실한 부분은 질문하거나 "확인 필요"로 표시한다.
- 이 스킬의 결과물은 초안/설계 지원이며, 공식 A-SPICE 심사나 ISO 26262 인증 판정이 아님을 명시한다.
