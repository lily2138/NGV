# SOLID 원칙, 인터페이스 통신 규칙, 아키텍처 스타일 카탈로그

## 1. SOLID 원칙 (컴포넌트/모듈 수준 적용)

이 스킬에서 SOLID는 클래스 단위가 아니라 **소프트웨어 컴포넌트(아키텍처 요소) 단위**로 적용한다.

| 원칙 | 컴포넌트 아키텍처 관점 적용 |
|---|---|
| S — 단일 책임(Single Responsibility) | 각 컴포넌트는 하나의 명확한 책임(변경 이유)만 가진다. 템플릿 4장(컴포넌트 책임) 작성 시, 한 컴포넌트에 서로 다른 이유로 바뀌는 책임이 섞여 있으면 분리를 제안한다. |
| O — 개방-폐쇄(Open-Closed) | 새로운 기능 추가 시 기존 컴포넌트의 내부 수정 없이 확장(새 구현체 추가, 플러그인/전략 패턴)으로 대응 가능해야 한다. 변경이 예상되는 지점(가변점)을 인터페이스 뒤로 숨긴다. |
| L — 리스코프 치환(Liskov Substitution) | 동일 인터페이스의 서로 다른 구현체(예: 실제 센서 드라이버 vs 시뮬레이션/스텁)는 호출자 입장에서 상호 치환 가능해야 한다 — SWE.4/SWE.5 단위·통합시험에서 스텁으로 대체 가능하려면 필수. |
| I — 인터페이스 분리(Interface Segregation) | 하나의 거대한 인터페이스를 여러 클라이언트가 공유하지 않고, 클라이언트별로 필요한 만 좁은 인터페이스로 나눈다 (템플릿 6장에서 인터페이스별 사용자를 명시). |
| D — 의존성 역전(Dependency Inversion) | 상위 수준 컴포넌트가 하위 수준 컴포넌트의 구체 구현이 아니라 추상 인터페이스에 의존하게 한다. **아래 2절 "인터페이스 전용 통신" 규칙의 근거가 되는 원칙.** |

## 2. 인터페이스 전용 통신 규칙 (필수, 예외 없음)

- 정적 의존성 다이어그램(템플릿 5장)에 나타나는 모든 컴포넌트 간 화살표는 **반드시 인터페이스(포트)를 통해서만** 그려야 한다. 컴포넌트 A가 컴포넌트 B의 구체 구현을 직접 참조/호출하는 관계는 허용하지 않는다.
- 모든 인터페이스는 템플릿 6장에 ID, 제공자(Provider), 사용자(Consumer), 데이터/시그니처, 호출조건, 시간제약, 오류계약을 명시한다. 인터페이스 없이 "암묵적으로 통신"하는 컴포넌트 쌍이 발견되면 반드시 지적하고 인터페이스를 신설하도록 제안한다.
- 전역변수/공유 메모리를 통한 암묵적 통신도 "인터페이스 없는 통신"으로 간주하고 지적한다 (ISO 26262-6 "제한된 전역변수 사용" 원칙과 연결, `iso26262-part6-architecture-principles.md` 참고).
- 순환 의존(A→B→A)은 두 컴포넌트가 인터페이스를 사이에 두더라도 원칙적으로 금지한다. 불가피한 경우, 콜백/이벤트 인터페이스로 방향을 명시적으로 분리하고 근거를 5장에 기록한다.

## 3. 높은 응집력 / 낮은 결합도 점검 체크리스트

컴포넌트를 확정하기 전에 아래를 점검한다 (하나라도 걸리면 컴포넌트 분해/재구성을 재검토):

- [ ] 이 컴포넌트를 수정해야 하는 이유(변경 사유)가 두 가지 이상인가? → 응집력 부족, 분리 검토
- [ ] 이 컴포넌트가 다른 컴포넌트의 내부 자료구조나 상태를 알아야 동작하는가? → 결합도 과다
- [ ] 이 컴포넌트에 대한 인터페이스가 5개 이상의 서로 무관한 오퍼레이션을 노출하는가? → 인터페이스 분리 원칙 위반 후보
- [ ] 두 컴포넌트가 항상 함께 변경되는가(하나를 바꾸면 반드시 다른 하나도 바꿔야 하는가)? → 숨은 결합, 경계 재설정 검토
- [ ] 하위 계층 컴포넌트가 상위 계층 컴포넌트를 알고 있는가(역방향 의존)? → 계층 위반, 의존성 역전 필요

## 4. 변경 유연성(Open-Closed) 확보 기법

- 가변점(향후 변경/확장 가능성이 높은 지점: 센서 종류, 통신 프로토콜, 알고리즘 변형 등)을 식별하고, 해당 지점을 인터페이스 뒤에 배치해 구현체 교체만으로 대응 가능하게 한다.
- 설정/파라미터화 가능한 값(캘리브레이션 값, 임계값 등)은 컴포넌트 코드가 아니라 별도 설정 데이터로 분리한다.
- 플랫폼/하드웨어 의존적 부분(HSI 등)은 별도의 어댑터 컴포넌트로 격리해, 상위 로직이 하드웨어 변경의 영향을 받지 않게 한다 (포트-어댑터 스타일, 5절 참고).

## 5. 아키텍처 스타일 후보 카탈로그 (제안 단계에서 사용)

아키텍처 제안 단계에서, 시스템 특성에 맞는 후보 2~3개를 아래에서 골라 비교표로 제시한다. 후보를 고를 때 확인할 시스템 특성: 실시간성 요구 수준, ASIL/안전무결성 수준, 변경/확장 빈도 예상, 팀 구조, 기존 자산(AUTOSAR 등 플랫폼) 재사용 여부.

| 스타일 | 개요 | 강점 | 약점/주의점 | 적합한 상황 |
|---|---|---|---|---|
| 계층형 (Layered) | 하드웨어 근접 계층부터 응용 계층까지 단방향 의존 계층 구성 | 이해 쉬움, ISO 26262 "계층적 구조" 원칙과 직접 부합 | 계층을 관통하는 횡단 관심사(로깅, 진단) 처리가 번거로움 | 대부분의 임베디드 ECU 소프트웨어의 기본 골격 |
| 포트-어댑터 (Hexagonal / Ports & Adapters) | 핵심 로직을 중앙에 두고, 외부(하드웨어/통신/UI)와의 연결은 포트(인터페이스)+어댑터로 격리 | 핵심 로직이 하드웨어/외부 변경에 영향받지 않음, 테스트 시 어댑터를 스텁으로 치환 용이(LSP) | 어댑터 계층 설계/관리 비용 | 하드웨어·프로토콜 변경이 잦거나 PC/SIL 시뮬레이션 검증이 중요한 경우 |
| 컴포넌트 기반 (AUTOSAR SWC 스타일) | Runnable-Port-Interface 단위로 컴포넌트를 정의하고 RTE/미들웨어가 통신을 중개 | 표준화된 통합, 재사용성, 플랫폼과의 정합성 | AUTOSAR 툴체인/RTE 생성 인프라 필요 | AUTOSAR 기반 양산 ECU 프로젝트 |
| 이벤트 기반 / 발행-구독 (Event-driven / Pub-Sub) | 컴포넌트가 이벤트를 발행/구독하며 느슨하게 결합 | 결합도 매우 낮음, 신규 구독자 추가가 기존 코드에 영향 없음(OCP) | 이벤트 흐름 추적/디버깅이 어려움, 타이밍 보장이 어려울 수 있음 | 다수의 독립적 기능이 공통 상태 변화에 반응해야 하는 경우 |
| 파이프-필터 (Pipe & Filter) | 데이터가 일련의 처리 단계(필터)를 순차 통과 | 각 필터의 책임이 명확(SRP), 필터 재배열/교체 용이 | 상태 공유가 필요한 경우 부적합 | 신호처리, 데이터 변환 파이프라인 성격의 기능 |
| 마이크로커널 (Microkernel / Plug-in) | 최소 핵심 + 플러그인 확장 | 기능 추가가 핵심에 영향 없음(OCP 극대화) | 핵심-플러그인 간 인터페이스 설계 난이도 높음 | 다양한 옵션/파생 변형이 많은 제품 라인 |

> 스타일은 상호 배타적이지 않다 (예: 전체는 계층형 + 하드웨어 경계는 포트-어댑터). 제안 시 "복합 적용"도 후보로 제시할 수 있다.
