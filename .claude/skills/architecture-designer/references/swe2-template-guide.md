# 저장소 템플릿(TPL-SWE2-001/002) 사용 가이드

> 이 문서는 `WP_Templates/` 아래 실제 템플릿 파일의 구조를 캐시해 둔 스냅샷이다. **작업 시작 시 반드시 아래 절차로 실제 템플릿 파일을 다시 확인**하라 — 사용자가 템플릿을 갱신했을 수 있으므로, 이 문서의 내용과 실제 파일이 다르면 실제 파일을 따른다.

## 0. 템플릿 원본 재확인 절차

1. `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`를 열어 SWE.2 관련 행(Template ID, 형식, 승인 버전, 적용 산출물 명명 규칙)을 확인한다. xlsx/docx를 직접 읽으려면 `xlsx`/`docx` 스킬을 사용하거나, Bash로 `unzip -p <파일> xl/worksheets/sheet1.xml` (xlsx) / `word/document.xml` (docx) 후 태그를 제거해 텍스트를 추출한다.
2. `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx`와 `TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`를 같은 방식으로 확인한다.
3. `WP_Templates/Engineering/README.md`의 작성 규칙(아래 2절에 요약)도 함께 확인한다.

## 1. 산출물 명명 규칙 (등록부 기준, 2026-09-17 스냅샷)

| Template ID | 형식 | 적용 산출물 파일명(예) | 필수 내용 |
|---|---|---|---|

| TPL-SWE2-002 | DRAWIO | `ENG-SWE2-002_SW 아키텍처 UML 원본.drawio` | (위와 동일 산출물 세트의 다이어그램 원본) |

- 베이스라인을 만들 때는 drawio에서 PNG를 함께 내보내 리뷰본/베이스라인에 첨부한다 (README 규칙).

## 2. TPL-SWE2-001 (SW 아키텍처 설계서) 목차 구조 — 반드시 이 순서/제목을 유지

```
표지: 템플릿 ID / 적용 프로세스(SWE.2) / 프로젝트 / 작성 문서 ID와 명칭 / 버전 및 베이스라인 / 작성자와 검토자
문서 통제: 변경 이력 표 (Revision/변경일/작성 역할/변경 내용/검토 상태) + 작성·검토·승인 상태 표 (구분/역할 또는 성명/상태/일자/증거 위치)
목차

1. 목적 및 적용범위
  1.1 목적
  1.2 적용범위
  1.3 적용 경계
2. 아키텍처 설계 원칙       — 분해, 결합도, 응집도, 인터페이스, 오류 격리, 변경 용이성에 적용한 원칙
3. 논리 아키텍처            — 소프트웨어 요소/계층/관계를 다이어그램과 함께
  3.1 아키텍처 요소         — 요소별 ID, 명칭, 목적, 제공 기능, 소유 책임
  3.2 관계와 제약           — 허용된 의존 방향, 호출 관계, 공유 자원, 금지된 결합
4. 컴포넌트 책임            — 컴포넌트별 책임, 입력, 출력, 상태, 오류 처리, 할당 요구사항
5. 정적 의존성              — 패키지/모듈/컴포넌트 정적 의존성, 순환 의존 방지 기준
6. 인터페이스 명세          — 인터페이스 ID, 제공자, 사용자, 데이터, 호출 조건, 시간 제약, 오류 계약
  6.1 내부 인터페이스       — 소프트웨어 요소 간 API/이벤트/데이터 저장소/동기화 규칙
  6.2 외부 인터페이스       — 하드웨어/통신/사용자/외부 서비스 경계와 변환 책임
7. 동적 동작                — 주요 시나리오 호출 순서, 데이터 흐름, 조건별 분기 (시퀀스/활동 관점)
8. 상태 전이                — 상태, 진입/종료 조건, 전이 이벤트, 가드, 금지 전이
9. 오류 격리와 안전 동작    — 오류 감지 위치, 전파 차단, 안전 상태, 복구, 진단정보 책임
10. 품질속성 분석           — 성능/신뢰성/유지보수성 등 주요 품질속성 시나리오와 설계 대응
11. 통합 전략               — 통합 단위, 순서, 인터페이스 검증, 스텁/드라이버, 회귀 범위
12. 요구사항 할당           — SW 요구사항을 아키텍처 요소/인터페이스에 할당, 누락/중복 확인
13. 자원 및 배포 경계       — 실행 노드, 프로세스, 메모리, CPU, 저장소, 배포 제약
14. 추적성                  — 요구사항/아키텍처 요소/상세설계/통합검증 간 연결
15. 참고자료                — 입력 요구사항, 적용 표준, 모델 원본, 설계 결정 기록
```

각 절 아래 "작성 안내" 문구는 실제 프로젝트 내용으로 **교체**한다 (안내문을 남겨두지 않는다).

### 이 스킬의 요구사항이 어느 절에 반영되는지

| 사용자 요구사항 | 대응 절 |
|---|---|
| A-SPICE/ISO 26262 원칙 준수 | 2장 |
| 높은 응집력/낮은 결합도 | 2장(원칙 서술) + 4장(컴포넌트 책임 — SRP 점검) + 5장(정적 의존성 — 결합도 점검) |
| 변경 유연성 | 2장(원칙) + 3.2절(관계와 제약에서 가변점/확장점 명시) |
| SOLID | 2장(원칙 서술에 SOLID 적용 내역 포함) |
| 인터페이스 정의 + 인터페이스 전용 통신 | 6장(6.1/6.2) — 5장의 모든 화살표는 6장의 인터페이스를 참조해야 함 |
| 통합 순서 정의 | 11장 |
| 아키텍처 후보 제안 → 사용자 선정 | 문서화 이전 단계 (제안 단계에서는 아직 이 템플릿을 채우지 않고, 후보 비교표만 별도로 제시) |
| 추적성 | 12장 + 14장, `requirements-analyst` 스킬의 RTM과 연동 |

## 3. TPL-SWE2-002 (SW 아키텍처 UML, drawio) 작성 규칙

- 도형 구성: `boundary`(시스템/설계 경계), `actor`(외부 액터/요소), `element`(대상 요소 — ID+명칭 표기), `edge`(관계 또는 인터페이스 — 반드시 인터페이스 이름/ID를 라벨로 표기).
- 작성 안내 메모(guide 도형)에 명시된 4가지를 반드시 채운다: ① 소프트웨어 요소와 계층, ② 제공 및 요구 인터페이스, ③ 허용된 의존 방향, ④ 요구사항 할당 ID.
- 안내용 더미 도형(`boundary`/`actor`/`element`/`guide`의 안내 텍스트)은 실제 값으로 교체하거나 삭제하고, 실제 요소 수만큼 복제해 사용한다.
- 하나의 drawio 파일 안에 여러 페이지(diagram)를 추가해 정적 구조도/동적 시퀀스도 등을 분리해 표현할 수 있다 (필요 시 3장용 구조도, 7장용 동적 다이어그램을 별도 페이지로).
- 베이스라인 시 PNG로 내보내 문서(TPL-SWE2-001 산출물) 3장/6장/7장에 삽입한다.
