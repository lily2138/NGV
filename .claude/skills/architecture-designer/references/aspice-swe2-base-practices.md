# A-SPICE 4.1 SWE.2 (소프트웨어 아키텍처 설계) 공식 원문 발췌

> 출처: VDA QMC "Automotive SPICE PAM 4.1" (공개 프리뷰), 4.4.2절. `aspice-cl2-auditor` 스킬의 `references/gp-2.1-2.2-checklist.md`와 함께, CL2 수준까지 고려한 산출물 작성 시 이 파일도 참고한다.

## 프로세스 목적
정적/동적 측면을 모두 포함하며 소프트웨어 요구사항과 일치하는, 분석된 소프트웨어 아키텍처를 수립하는 것.

## 프로세스 성과(outcome)
1. 정적/동적 측면을 포함한 소프트웨어 아키텍처가 설계된다.
2. 소프트웨어 아키텍처가 정의된 기준에 따라 분석된다.
3. 소프트웨어 아키텍처와 소프트웨어 요구사항 사이에 일관성과 양방향 추적성이 확립된다.
4. 소프트웨어 아키텍처가 합의되고 관련된 모든 당사자에게 전달(공유)된다.

## 기본관행(Base Practices)

**SWE.2.BP1 — 소프트웨어 아키텍처의 정적 측면을 명시한다.** 기능/비기능 소프트웨어 요구사항과 관련하여 외부 인터페이스, 그리고 인터페이스와 관계를 가진 소프트웨어 컴포넌트의 정의된 집합을 포함해 정적 측면을 명시·문서화한다.
- 참고: HSI(하드웨어-소프트웨어 인터페이스) 정의는 하드웨어 설계를 포함하므로 시스템 설계(SYS.3)의 영역이다.

**SWE.2.BP2 — 소프트웨어 아키텍처의 동적 측면을 명시한다.** 기능/비기능 소프트웨어 요구사항과 관련하여, 서로 다른 소프트웨어 모드에서의 소프트웨어 컴포넌트 행동과 상호작용, 동시성(concurrency) 측면을 포함해 동적 측면을 명시·문서화한다.
- 참고: 동시성 측면의 예 — 애플리케이션 관련 인터럽트 처리, 선점형 처리, 멀티스레딩.
- 참고: 행동 서술의 예 — 자연어 또는 준형식(semi-formal) 표기법(예: SysML, UML).

**SWE.2.BP3 — 소프트웨어 아키텍처를 분석한다.** 관련 기술적 설계 측면에 대해 소프트웨어 아키텍처를 분석하고, 프로젝트 관리를 위한 프로젝트 추정치를 지원한다. 아키텍처 설계 결정의 근거(rationale)를 문서화한다.
- 참고: 분석에는 기존 소프트웨어 컴포넌트의 현재 적용 적합성 검토가 포함될 수 있다.
- 참고: 기술적 측면 분석에 적합한 방법의 예 — 프로토타입, 시뮬레이션, 정성적 분석.
- 참고: 기술적 측면의 예 — 기능성, 타이밍, 자원 소비(ROM/RAM/EEPROM/Data Flash/CPU 부하 등).
- 참고: 설계 근거의 예 — 실사용 검증됨(proven-in-use), 소프트웨어 프레임워크/제품라인 재사용, 자체개발-구매(make-or-buy) 결정, 점진적(set-based) 설계.

**SWE.2.BP4 — 일관성을 확보하고 양방향 추적성을 확립한다.** 소프트웨어 아키텍처와 소프트웨어 요구사항 사이의 일관성을 확보하고 양방향 추적성을 확립한다.
- 참고: 아키텍처가 추적되지 않는 비기능 요구사항(예: 개발 프로세스 요구사항)이 있을 수 있으나, 이 또한 검증 대상이다.
- 참고: 양방향 추적성은 일관성을 뒷받침하고, 변경요청의 영향분석과 커버리지 입증을 용이하게 한다. 링크의 존재 자체가 정보의 일관성을 보장하지는 않는다.

**SWE.2.BP5 — 합의된 소프트웨어 아키텍처를 전달(공유)한다.** 합의된 소프트웨어 아키텍처를 관련된 모든 당사자에게 전달한다.

## 출력 정보항목(Output Information Items)
- 04-04 Software Architecture (소프트웨어 아키텍처)
- 13-51 Consistency Evidence (일관성 증적)
- 13-52 Communication Evidence (전달/공유 증적)
- 15-51 Analysis Results (분석 결과)

## 이 스킬에 대한 시사점

- BP1(정적)·BP2(동적) 모두 산출물에 포함되어야 한다 — 이 스킬의 템플릿 3장(논리 아키텍처)·6장(인터페이스)이 정적 측면, 7장(동적 동작)·8장(상태 전이)이 동적 측면에 대응한다.
- BP3의 "분석" — 템플릿 10장(품질속성 분석)에서 성능/자원/신뢰성 등 기술적 측면을 근거와 함께 분석·기록한다.
- BP4의 양방향 추적성 — 템플릿 12장(요구사항 할당)·14장(추적성)에서 확보하며, `requirements-analyst` 스킬이 관리하는 추적성 매트릭스(RTM)와 연동한다.
- BP5의 "전달/공유" — 산출물을 작성한 뒤 리뷰/승인 절차(템플릿의 "작성 검토 승인 상태" 표)를 거쳐 관련자에게 공유했다는 증적(회의록, 배포 이력 등)을 남기도록 안내한다.
