# ISO 26262-6 기반 소프트웨어 아키텍처 설계 원칙 (참고 요약)

> 주의: 이 문서는 ISO 26262(2018) Part 6, Clause 7 "Software architectural design"의 널리 알려진 개념(Table 2/3/4 계열)을 공개 2차 자료를 바탕으로 정리한 **참고용 요약**이며 표준 원문을 그대로 인용한 것이 아니다. 실제 안전성 인증 산출물로 확정하기 전에는 조직이 보유한 정식 ISO 26262-6:2018 문서로 표·조항 번호를 대조 확인할 것.

## 아키텍처 설계 목적 (Clause 7 개념)
- 소프트웨어 요구사항(안전요구사항 포함)을 만족하는 아키텍처를 개발한다.
- 해당 ASIL에 맞는 방법으로 아키텍처를 검증한다.
- 이후 상세설계·구현을 지원할 수 있도록 충분히 구체화한다.

## 정적/동적 측면 (Clause 7.4.5 개념)
- **정적 측면**: 소프트웨어 컴포넌트의 계층 구조, 컴포넌트 간 인터페이스와 의존관계. 통상 클래스/컴포넌트 다이어그램류로 표현.
- **동적 측면**: 컴포넌트 간 데이터 흐름과 제어 흐름, 시나리오별 상호작용. 통상 시퀀스/활동/상태 다이어그램류로 표현.
- 정적/동적 측면 모두 문서화해야 하며, 이는 A-SPICE SWE.2.BP1/BP2와 정확히 대응한다.

## 아키텍처 설계 원칙 (Table 3 계열 개념) — 이 스킬이 강제하는 핵심 규칙

아래 원칙들은 ASIL이 높아질수록 권고 강도가 강해지는(+, ++) 구조이나, 이 스킬은 **ASIL과 무관하게 항상 적용**하는 것을 기본으로 한다 (사용자가 명시적으로 완화를 요청하지 않는 한).

| 원칙 | 설명 | 이 스킬에서의 적용 |
|---|---|---|
| 계층적 구조 (Hierarchical structure) | 아키텍처를 여러 추상화 계층으로 구성 | 템플릿 3장에 계층 구조 명시 |
| **컴포넌트 내 높은 응집력 (High cohesion)** | 하나의 컴포넌트는 밀접하게 관련된 책임만 가진다 | **필수** — 4장(컴포넌트 책임) 작성 시 단일 책임 원칙과 함께 점검 |
| **컴포넌트 간 낮은 결합도 / 제한된 인터페이스 크기 (Low coupling / restricted interface size)** | 컴포넌트는 필요한 최소한의 인터페이스로만 연결 | **필수** — 6장(인터페이스 명세)에서 인터페이스 개수·크기를 최소화하고 근거를 남긴다 |
| 적절한 스케줄링 속성 | 태스크/스레드의 우선순위와 실행 주기가 근거를 가지고 정의됨 | 7장(동적 동작)에 반영 |
| 적절한 공간적 분리 (Spatial isolation, 2018 신설) | 서로 다른 ASIL/무결성 수준의 컴포넌트를 메모리/실행 공간 상 분리 | 13장(자원 및 배포 경계)에서 ASIL 혼재 시 분리 방안 기록 |
| 공유자원의 적절한 관리 (Shared resource management, 2018 신설) | 공유 메모리/자원에 대한 접근 통제(뮤텍스 등) | 9장(오류 격리와 안전 동작)·13장에 반영 |
| 제한된 전역변수 사용 | 컴포넌트 간 은닉된 결합(전역변수를 통한 암묵적 의존)을 피함 | 5장(정적 의존성)에서 전역 상태를 통한 숨은 의존을 식별·금지 |

## 표기법 (Notations, Table 2 계열 개념)
- 비형식(자연어), 준형식(SysML/UML 등 semi-formal), 형식(수학적/formal) 표기법이 있으며, ASIL이 높아질수록 준형식/형식 표기법이 강하게 권고된다.
- 이 스킬은 ASIL과 무관하게 **준형식 표기법(UML/SysML, 본 저장소에서는 draw.io 기반 UML)** 사용을 기본으로 한다 — 자연어만으로는 명확성·검증가능성을 담보하기 어렵기 때문.

## 아키텍처 검증 방법 (Table 4 계열 개념)
아키텍처가 요구사항을 만족하는지 검증하는 데 사용 가능한 방법(택일 또는 조합):
- 워크스루(walk-through), 인스펙션(inspection) — 리뷰 기반
- 시뮬레이션, 프로토타이핑 — 동적 검증
- 정형검증(formal verification) — 높은 ASIL에서 강하게 권고
- 제어흐름분석(control flow analysis), 데이터흐름분석(data flow analysis) — 정적 분석

템플릿 10장(품질속성 분석)·11장(통합 전략) 작성 시, 위 방법 중 실제로 수행 가능한 것을 명시한다 (수행 불가능한 방법을 나열하지 않는다 — `requirements-analyst` 스킬의 "실행 가능한 검증방안" 원칙과 동일하게 적용).

## SYS.3 / SWE.3와의 경계
- 하드웨어-소프트웨어 인터페이스(HSI) 정의는 시스템 설계(SYS.3)의 영역이며, 이 스킬(SWE.2)은 이를 입력으로 받아 참조한다.
- 컴포넌트 내부의 함수 단위 상세 설계는 SWE.3(상세설계)의 영역이며, 이 스킬은 컴포넌트/인터페이스 수준까지만 다룬다.
