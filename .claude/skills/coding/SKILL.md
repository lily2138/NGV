# 구현(코딩) 스킬

이 스킬은 `detailed-designer`(SWE.3) 산출물을 실제 Python 코드와 단위테스트로 구현하는 절차를 정의한다. **반드시 `tdd` 스킬과 함께 사용한다** — 이 스킬은 "무엇을 지켜야 하는지"(품질 지표, 언어/도구, 인터페이스 충실도)를, `tdd` 스킬은 "어떤 순서로 작업하는지"(Red-Green-Refactor)를 정의한다.

## 참고자료 (필요할 때 불러오고, 통째로 대화창에 붙여넣지 말 것)

- `references/python-quality-metrics.md` — CLAUDE.md 구현 지침의 4대 지표(함수 라인수≤50, 순환복잡도≤10, 중복코드≤7라인, 주석≥20%)와 CLAUDE.md 단위 테스트 지침의 Branch 커버리지 100%를 오픈소스 도구(`lizard`, `pylint`, `radon`, `coverage.py`)로 측정하는 구체적 명령과 임계값 설정.
- `references/doxygen-comment-style.md` — Doxygen 방식(`"""!` + `@brief`/`@param`/`@return`/`@exception`) 주석 템플릿과, 상세설계 함수 계약을 주석으로 옮기는 방법.

> CLAUDE.md 구현 지침은 이 저장소의 프로젝트 정책이며 외부 표준이 아니다 — 별도의 "참고 요약" 면책 문구는 필요 없다. 다만 명명 규칙(camelCase)은 PEP8 표준 관례(snake_case)와 다른 이 프로젝트만의 명시적 오버라이드임을 항상 인지한다.

## 0. 사전 확인 (매번 수행)

1. 구현 대상 SWE.3 상세설계 산출물(`ENG-SWE3-001` 등: 함수 계약, 알고리즘, 정책 의사결정표, 상태전이)과 SWE.2 아키텍처 산출물(`ENG-SWE2-001`/`002`: 컴포넌트 인터페이스)의 위치를 Read/Grep/Glob으로 확인한다. 상세설계 근거 없이 코드를 창작하지 않는다 — 못 찾으면 사용자에게 위치를 확인한다.
2. 소스코드/테스트코드를 저장할 디렉터리 구조(예: `src/`, `tests/`)가 저장소에 없다면, 임의로 새 구조를 만들지 말고 사용자에게 규칙을 확인한다.
3. 프로젝트에 이미 `.pylintrc`/lint 설정이 있는지 확인한다. 없으면 `python-quality-metrics.md` 4절의 camelCase 설정을 반영한 설정 파일을 새로 만들 것을 제안한다.

## 1. 구현 절차

1. **인터페이스/계약 확인**: 구현할 함수의 SWE.2 인터페이스(외부 시그니처)와 SWE.3 함수 계약(사전조건/사후조건/부작용/예외/시간제약)을 정확히 파악한다. 설계에 없는 동작을 임의로 추가하거나, 설계된 인터페이스를 바꾸지 않는다 — 설계가 불완전해 구현이 불가능하면 임의로 채우지 말고 `detailed-designer`/`architecture-designer` 쪽 보완을 사용자에게 요청한다.
2. **TDD 진입**: `tdd` 스킬을 호출해 Red-Green-Refactor 절차를 시작한다. 함수 계약의 사전조건/사후조건/경계값/예외 조건이 각각 최소 하나 이상의 테스트 케이스로 다뤄지도록 한다 (상세설계의 정책 의사결정표·경계값 목록을 테스트 케이스 목록의 근거로 사용).
3. **구현**: `unittest`가 통과하는 최소 구현을 Python 3.14로 작성한다. 함수/변수명은 `python-quality-metrics.md` 4절의 camelCase 규칙(3글자 이상)을 따른다.
4. **주석**: `doxygen-comment-style.md` 형식으로 Doxygen 주석을 작성하며, 상세설계 함수 계약 내용을 `@param`/`@return`/`@exception`으로 옮긴다.
5. **품질 게이트 (구현 완료 전 필수)**: `python-quality-metrics.md`의 도구(`lizard`, `pylint duplicate-code`, `radon raw`, 명명 검사, `coverage.py --branch`)를 모두 실행한다.
   - 함수 라인수(순수 코드) ≤ 50, 순환복잡도 ≤ 10, 중복 코드 8라인 미만, 주석 비율 ≥ 20%, 명명 규칙(3자 이상 camelCase) 위반 없음, **Branch 커버리지 100%** — 전부 만족해야 "구현 완료"로 보고한다.
   - 위반이 있으면 `tdd` 스킬의 Refactor 단계로 돌아가 리팩터링하거나(지표 위반) 누락된 분기를 실행하는 테스트를 추가한 뒤(Branch 커버리지 미달) 재확인한다 (테스트가 깨지지 않는 범위 내에서 리팩터링).
6. **추적성**: `requirements-analyst`가 관리하는 RTM(`ENG-TRC-001`)의 `Code` 컬럼(및 이미 있다면 `SWE.4` 컬럼에 작성한 unittest 테스트 ID)을 같은 작업 안에서 갱신한다. 상세설계 요소 하나가 여러 함수로 구현되거나, 함수 하나가 여러 설계 요소를 구현하는 경우 매핑을 명확히 기록한다.
7. **일관성 점검**: 새로 작성한 코드가 같은 컴포넌트 내 기존 코드의 명명/에러 처리 관례와 상충하지 않는지 확인한다. 상충이 발견되면 임의로 하나를 택하지 말고 사용자에게 알린다.
8. **결과 보고**: 구현한 파일 목록, 테스트 파일 목록, 품질 지표 측정 결과(지표별 수치와 통과 여부), RTM 갱신분을 요약해 보고한다.

## 출력 시 유의사항

- 이 저장소의 `WP_Templates`에는 소스코드/구현 자체에 대한 문서 템플릿이 없다 (코드와 테스트 코드 자체가 산출물이다). 다만 SWE.3 폴더의 `TPL-SBOM-001`(오픈소스 의존성 목록)은 외부 라이브러리를 도입할 때 갱신 대상이다.
- 근거 없는 구현(설계에 없는 기능 추가)을 하지 않는다. 설계 근거가 불명확하면 질문한다.
- 이 스킬의 결과물은 구현 초안이며, 공식 A-SPICE 심사 판정이 아님을 명시한다.
