# SWE.3 상세설계에서 테스트 케이스 도출하기

TDD의 0단계(RED 이전)에서 사용한다. 테스트 케이스를 지어내지 말고, 대상 함수의 SWE.3 함수 계약(`detailed-designer` 스킬의 `unit-design-quality.md` 1절)과 그 외 상세설계 절(정책 의사결정표, 상태전이)에서만 도출한다.

> 아래 표의 기법 정의는 `../../_shared/references/test-design-techniques.md`(전 단계 공용 taxonomy)를 따른다 — 여기서는 SWE.3 상세설계의 어느 절이 어느 기법에 대응하는지만 매핑한다. 조건 조합이 많아 의사결정표의 전수 조합이 비현실적이면, 공용 문서의 페어와이즈(PICT) 기법으로 대체한다.

## 도출 대상과 대응하는 테스트 기법

| 상세설계 근거 | 테스트 기법 | 케이스 종류 |
|---|---|---|
| 사전조건을 만족하는 정상 입력 (동등분할별로 최소 1개) | 동등분할(equivalence partitioning) | positive |
| 상세설계 6장(핵심 알고리즘)에 명시된 경계값 각각 | 경계값분석(boundary value analysis) | positive 또는 negative (경계가 유효/무효 여부에 따라) |
| 사전조건을 위반하는 입력 → 상세설계 10장(오류와 방어 동작)에 명시된 예외/오류 처리 | 오류추측(error guessing) 또는 경계값분석 | negative |
| 정책 의사결정표(상세설계 7장)의 각 행(조건 조합) | 의사결정표 기반(decision table testing) | 표에 명시된 기대 동작에 따라 positive/negative |
| 상태전이 상세(상세설계 8장)의 상태×이벤트 조합 — 허용 전이와 금지 전이 모두 | 상태전이 기반(state transition testing) | 허용 전이는 positive, 금지 전이는 negative |

## 절차

1. 대상 함수/단위의 상세설계 절(5~8, 10장)을 읽는다. 근거 문서를 찾지 못하면 테스트 케이스를 지어내지 말고 사용자에게 상세설계 위치를 확인한다.
2. 위 표를 기준으로 가능한 모든 케이스를 나열한다. 케이스가 지나치게 많아지면(예: 조합 폭발), 동등한 케이스를 그룹화한 근거를 남기고 대표 케이스만 선정한다.
3. 각 케이스에 다음을 함께 기록한다 (테스트 함수의 Doxygen 주석에 그대로 옮겨진다):
   - **@technique**: 위 표의 기법명
   - **@case**: `positive` 또는 `negative`
4. 부정(negative) 케이스가 0개인 함수는 없는지 확인한다 — 상세설계에 예외/오류 조건이 전혀 없다고 명시적으로 확인된 경우만 예외로 허용한다.
5. 이 목록을 테스트 작성 전에 사용자에게 제시하거나 코드/커밋에 남겨, 나중에 커버리지를 검증할 수 있게 한다.

## 완료 판정에 포함할 것

`tdd` 스킬의 완료 전 점검 체크리스트에 더해, 다음이 모두 참이어야 이 함수의 테스트 케이스 도출이 완료된 것으로 본다:

- 사전조건을 만족하는 입력, 경계값, 사전조건 위반, (해당 시) 의사결정표 각 행, (해당 시) 상태×이벤트 조합 중 테스트로 커버되지 않은 것이 없다.
- 각 테스트 함수의 Doxygen 주석에 `@technique`과 `@case`가 기록되어 있다.
- 부정 케이스 누락이 있다면 갭으로 보고했다 (묵인하고 넘어가지 않았다).
