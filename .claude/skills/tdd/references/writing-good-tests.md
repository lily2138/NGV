# 정직한 테스트 작성하기

> 출처: [obra/superpowers](https://github.com/obra/superpowers)의 `writing-good-tests.md`를 Python/`unittest` 기준으로 번역·각색.

**이 문서를 불러올 때:** 테스트를 새로 작성하거나 수정할 때, 모의객체(mock)를 추가할 때, 테스트용 헬퍼/정리(cleanup) 메서드를 추가할 때.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재한다. 모든 것을 지배하는 두 원칙:

```
1. 모든 테스트는 자신이 잡아내는 깨짐의 이름을 댈 수 있어야 한다
2. 모든 테스트는 실제 대상을 실행해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다: 먼저 작성되어 실제 코드에 대해 실패하는 것을 지켜본 테스트는 이미 "실패할 수 있음"을 증명한 것이고, 실제 의존성이 느리거나 외부 자원일 때만 모킹할 자격을 얻는다.

## 원칙 1: 깨짐의 이름을 대라

테스트 본문을 쓰기 전에 먼저 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 조건, 깨진 계약 중 하나를 잡아낼 때 존재 가치가 있다.

**기대값은 독립적으로 계산하라.** 리터럴 값과 손으로 확인한 픽스처를 사용한다. 리터럴 `want` 값을 사용하는 테이블 기반 테스트를 선호한다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다:

```python
# ❌ 거울 어서션: 같은 함수로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# ✅ 손으로 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 마라.** 의도적인 설계 결정만 실패시킬 수 있는 테스트 — 상수값, 정확한 메시지 문구, 내부 구조 — 는 리팩터링 때마다 울리고 버그 앞에서는 잠든다. 결정 자체가 아니라 그 결정에 의존하는 동작을 테스트한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출은 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**텍스트가 아니라 동작을 검증하라.** 스크립트나 설정 파일에 특정 줄이 있는지 확인하는 것은 소스가 소스라는 것만 증명한다. 스크립트는 통제된 입력으로 실행해 출력·부작용·종료 코드를 검증한다.

**프레임워크가 아니라 자신의 코드를 검증하라.** 코드의 경계에서 만드는 계약(등록하는 라우트, 실행하는 쿼리, 만들어내는 페이로드)을 테스트한다. 상위 프레임워크의 동작은 그 프레임워크 유지보수자의 몫이다 — 예를 들어 "라우터가 등록된 핸들러를 호출한다"는 프레임워크의 테스트이지 우리 테스트가 아니다. 상위 동작이 예상과 다르게 놀라웠다면, 그 가정을 명시하는 좁은 특성화(characterization) 테스트 하나만 작성한다. 생성자, getter, 상수, 단순 위임 함수는 검증·정규화·기본값 설정·유도·강제·부작용 중 하나를 수행할 때만 테스트할 가치가 있다 — 그렇지 않으면 그것에 의존하는 첫 번째 눈에 보이는 결과를 검증한다.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  어떤 프로덕션 변경이 이 테스트를 실패시킬지 이름을 댄다.

  이름을 댈 수 없다            → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"      → 산출물을 실행하고 그 효과를 검증
  의도적 결정만 잡아낸다        → 변경 감지기다; 그 결정에 의존하는 동작을 검증

  기대값이 검증 대상 코드 없이 도출되었는지 확인한다.
  만약 그 코드나 헬퍼의 로직을 재사용한다면:
    리터럴이나 손으로 확인한 픽스처로 교체한다
```

## 원칙 2: 실제 대상을 실행하라

**모의객체는 어서션의 근거가 되지 못한다.** 모의객체가 존재하면 통과하고 없으면 실패하는 어서션은 그 컴포넌트에 대해 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 검증한다. 모의객체 자체를 검증하고 있다면, 모킹을 풀거나 그 어서션을 지운다.

```python
# ✅ 실제 동작 검증
self.assertTrue(pageContains(response, "환영합니다"))

# ❌ 모의객체 존재 여부만 검증
self.assertTrue(mockRenderer.called)
```

**your human partner's correction:** "지금 모의객체의 동작을 테스트하고 있는 건 아닌가?"

**적절한 수준에서 모킹하라.** 실제 메서드를 대체하기 전에 그 모든 부작용을 먼저 파악한다. 느리거나 외부에 있는 연산만 모킹하고, 테스트가 실제로 의존하는 부분은 실제로 둔다. 확신이 없으면 먼저 실제 구현으로 테스트를 돌려보고 실제로 무슨 일이 일어나는지 관찰한다.

```python
# ❌ 모킹이 중복 탐지 로직이 읽는 설정 기록까지 삼켜버림
with patch("toolCatalog.discoverAndCacheTools", return_value=None):
    ...

# ✅ 느린 서버 기동만 모킹하고, 테스트가 의존하는 설정 기록은 실제로 둔다
with patch("mcpServerManager.MCPServerManager"):
    ...
```

**대역(double)을 구체적으로 만들어라.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 검증한다 — 무엇이든 받아들이는 가짜 객체는 아무것도 검증하지 못한다. 각 분기(성공, 오류, 잘못된 입력)마다 별도의 픽스처나 스파이를 둬서, 엉뚱한 분기가 기대를 만족시키지 못하게 한다.

**모의 응답은 실제 구조를 완전히 반영하라.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 모든 문서화된 필드를 포함해 모킹한다. 부분적인 모킹은 하위 코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하지만 실제 통합은 깨진다.

**프로덕션 클래스에는 프로덕션 메서드만 둔다.** 테스트에서만 필요한 정리(cleanup) 코드를 프로덕션 클래스의 `destroy()` 같은 메서드로 만들지 않는다. 자문한다: 이 메서드는 테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 "그렇다"면 테스트 유틸리티로 옮긴다.

**모킹이 비대해지면 실제 컴포넌트를 선호하라.** 모킹 설정이 테스트 로직보다 커지거나, 모의객체에 실제 컴포넌트의 메서드가 빠져 있거나, 모의객체가 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 사용하는 통합 테스트로 전환한다. **your human partner's question:** "여기서 정말 모의객체가 필요한가?"

### 게이트 함수

```
모의객체나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 둔 채
  느리거나 외부에 있는 수준만 모킹한다.

  모의 응답이 실제 구조를 완전히 반영하는지 확인한다.

  테스트에서만 호출되는 메서드는 프로덕션 클래스가 아니라 테스트 유틸리티에 둔다.

  지금 모의객체 자체를 검증하려는 것인가?
    모킹을 풀거나 그 어서션을 지운다.
```

## 테스트는 구현과 함께 출시된다

TDD 사이클 — 실패하는 테스트, 최소 구현, 리팩터링 — 이 곧 "완료"의 의미다. 그 동작이 필요로 하는 테스트만 딱 그만큼 만든다. 사소한 코드와 사람을 위한 설명문은 테스트가 필요 없고, 그저 "절차를 만족시키기 위해" 쓴 테스트는 영원히 유지보수 비용만 남긴다.

## 돌연변이 점검 (Mutation Check)

끝내기 전에, 머릿속으로 프로덕션 코드를 돌연변이시켜본다. 현실적인 돌연변이마다 적어도 하나의 테스트가 실패해야 한다:

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 누락된 상태 변경이나 부작용
- 빈 값이나 기본값 반환
- 0, 빈 값, None, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

아무 테스트도 잡아내지 못하는 돌연변이가 있다면, 그 동작은 보호되지 않은 것이거나 테스트가 동어반복(tautological)인 것이다.

## 빠른 참조

| 상황 | 할 일 |
|---|---|
| 아무 테스트나 작성할 때 | 그것이 잡아내는 깨짐의 이름을 댄다 — 버그이지, 설계 결정이 아니어야 한다 |
| 기대값을 만들 때 | 손으로 도출한다; 검증 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행하거나 그 소비자를 압박 테스트한다; 절대 텍스트를 grep하지 않는다 |
| 의존성 테스트에 손이 갈 때 | 자신의 경계 계약을 테스트한다, 그들의 문서화된 메커니즘이 아니라 |
| 모킹된 요소를 검증하고 싶을 때 | 실제 컴포넌트를 테스트하거나 모킹을 푼다 |
| 메서드를 모킹하려 할 때 | 그 부작용을 먼저 파악한다; 느리거나 외부인 수준만 모킹한다 |
| 모의 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트만 쓰는 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| 모킹 설정이 커질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 끝낼 때 | 돌연변이 점검을 수행한다 |

## 경고 신호

- 준비(setup)와 어서션이 같은 객체를 공유해서 항상 같음이 보장됨
- 패닉·크래시·선택자 누락을 통해서만 테스트가 실패할 수 있음
- 의도적인 모든 변경에서 실패하고, 실수로 인한 손상에서는 실패하지 않음
- 기대값이 반복문·빌더·헬퍼 뒤에 숨어 있음
- 테스트가 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지 확인함
- 프레임워크만 남아 있어도 여전히 통과할 테스트임
- 커버리지를 위해 존재하며 부작용이나 결과를 확인하지 않음
- `*-mock` 테스트 ID를 검증하거나, 모의객체를 제거하면 실패함
- 어떤 메서드가 테스트 파일에서만 호출됨
- 모킹 설정이 테스트의 절반 이상을 차지하거나, 왜 그 모킹이 필요한지 설명할 수 없음
- "혹시 몰라서" 모킹함
