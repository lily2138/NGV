# 테스트 주도 개발 (TDD)

> 이 스킬은 공개 저장소 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬 구조와 원칙을 이 프로젝트(Python 3.14 + `unittest`, A-SPICE SWE.3 상세설계 기반, Doxygen 주석 규칙)에 맞게 번역·각색한 것이다.

## 개요

테스트를 먼저 작성한다. 실패하는 것을 지켜본다. 통과시키는 최소한의 코드를 작성한다.

**핵심 원칙:** 테스트가 실패하는 것을 직접 지켜보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.**

## 언제 사용하는가

**항상:**
- 신규 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외 (반드시 사용자에게 먼저 확인):**
- 일회성 프로토타입
- 자동 생성된 코드
- 설정 파일

"이번만 TDD를 건너뛰자"는 생각이 들면 멈춘다. 그것은 합리화다.

## 철칙 (Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다
```

테스트보다 코드를 먼저 썼는가? 삭제하고 처음부터 다시 한다.

**예외 없음:**
- "참고용"으로 남겨두지 않는다
- 테스트를 작성하며 그 코드를 "그대로 옮기지" 않는다
- 쳐다보지도 않는다
- 삭제는 삭제다

테스트로부터 새로 구현한다. 예외 없음.

## 0단계 — 테스트 케이스 도출 (RED 이전)

테스트를 작성하기 전에, 대상 함수의 SWE.3 함수 계약(`detailed-designer` 스킬의 `unit-design-quality.md` 1절)에서 테스트 케이스를 도출한다 — 지어내지 않고 설계 문서 근거로만 도출한다. 자세한 절차는 `references/swe3-test-case-derivation.md`를 참고한다. 각 케이스마다 **사용 기법**(동등분할/경계값분석/의사결정표 기반/상태전이 기반/오류추측)과 **긍정/부정 케이스 여부**를 함께 기록한다.

## Red-Green-Refactor

```
RED(실패하는 테스트 작성) → RED 확인(제대로 실패하는지 검증)
  → GREEN(최소 구현) → GREEN 확인(전부 통과하는지 검증)
  → REFACTOR(테스트를 유지하며 정리, 여기서 품질 게이트 점검)
  → 다음 테스트 케이스로 반복
```

### RED — 실패하는 테스트 작성

하나의 동작을 보여주는 최소한의 테스트 하나를 작성한다. 모든 테스트 함수는 **Doxygen 형식 주석으로 목적·기법·긍정/부정 여부**를 명시한다 (`coding` 스킬의 `doxygen-comment-style.md`와 동일한 태그 체계).

<좋은 예>
```python
class TestRetryOperation(unittest.TestCase):
    def testSucceedsAfterThreeAttempts(self):
        """!
        @brief 세 번째 시도에서 성공하면 그 결과를 반환하는지 검증한다.
        @technique 오류추측 (일시적 실패 후 회복 시나리오)
        @case positive
        """
        attempts = {"count": 0}

        def operation():
            attempts["count"] += 1
            if attempts["count"] < 3:
                raise RuntimeError("fail")
            return "success"

        result = retryOperation(operation)

        self.assertEqual(result, "success")
        self.assertEqual(attempts["count"], 3)
```
명확한 이름, 실제 동작 검증, 한 가지만 검증

<나쁜 예>
```python
def testRetryWorks(self):
    mockOp = Mock(side_effect=[RuntimeError(), RuntimeError(), "success"])
    retryOperation(mockOp)
    self.assertEqual(mockOp.call_count, 3)
```
모호한 이름, 실제 코드가 아니라 모의객체 호출 여부만 검증

**요구사항:**
- 하나의 동작만 검증
- 명확한 이름 (`test`로 시작하는 camelCase, `coding` 스킬의 명명 규칙 준수)
- 실제 코드 (불가피한 경우가 아니면 모킹하지 않는다)
- Doxygen 주석(`@brief`/`@technique`/`@case`) 필수

### RED 확인 — 실패를 지켜본다

**필수. 절대 건너뛰지 않는다.**

```bash
python -m unittest <테스트 모듈 경로>
```

확인할 것:
- 테스트가 실패한다 (에러가 아니라 실패)
- 실패 메시지가 예상과 일치한다
- 기능이 아직 없어서 실패하는 것이지, 오타 때문이 아니다

**테스트가 통과한다?** 이미 존재하는 동작을 테스트한 것이다 — 테스트를 고친다.
**테스트가 에러를 낸다?** 에러를 고치고 "제대로" 실패할 때까지 다시 실행한다.

### GREEN — 최소 구현

테스트를 통과시키는 가장 단순한 코드를 작성한다.

<좋은 예>
```python
def retryOperation(operation, maxAttempts=3):
    for attempt in range(maxAttempts):
        try:
            return operation()
        except Exception:
            if attempt == maxAttempts - 1:
                raise
```
통과에 필요한 만큼만

<나쁜 예>
```python
def retryOperation(operation, maxAttempts=3, backoff="linear", onRetry=None):
    # YAGNI: 아직 아무 테스트도 요구하지 않은 옵션들
    ...
```
과도한 설계

기능을 추가하거나, 다른 코드를 리팩터링하거나, 테스트가 요구하지 않은 것까지 "개선"하지 않는다.

**이 프로젝트 규칙**: SWE.2/SWE.3에서 정의된 함수 시그니처(인터페이스·계약)를 바꾸지 않는다. 함수/변수명은 3글자 이상 camelCase(`coding` 스킬의 명명 규칙)를 따른다.

### GREEN 확인 — 통과를 지켜본다

**필수.**

```bash
python -m unittest <테스트 모듈 경로>
```

확인할 것:
- 테스트가 통과한다
- 다른 테스트도 계속 통과한다
- 출력이 깨끗하다 (에러/경고 없음)

**테스트가 실패한다?** 코드를 고친다, 테스트를 고치지 않는다.
**다른 테스트가 실패한다?** 지금 바로 고친다.

### REFACTOR — 정리

Green 상태에서만 진행한다:
- 중복 제거
- 이름 개선
- 헬퍼 함수 추출

테스트는 계속 통과 상태로 유지한다. 새로운 동작을 추가하지 않는다.

**이 프로젝트 규칙**: 이 단계에서 `coding` 스킬의 품질 게이트(`python-quality-metrics.md`: 함수 라인수≤50, 순환복잡도≤10, 중복코드 8라인 미만, 주석비율≥20%, camelCase 명명, **Branch 커버리지 100%**)를 점검하고 위반을 해소한다. Branch 커버리지가 100%에 못 미치면(누락된 분기가 있으면) 0단계로 돌아가 그 분기를 실행하는 테스트 케이스를 추가한다 — 이는 곧 다음 RED 사이클이다. 리팩터링으로 함수 시그니처가 바뀌어야 한다면, 이는 SWE.2/SWE.3 설계 변경에 해당하므로 멈추고 사용자에게 보고한다 — 임의로 인터페이스를 바꾸지 않는다.

### 반복

0단계에서 도출한 다음 테스트 케이스에 대해 RED→GREEN→REFACTOR를 반복한다. 목록을 모두 소진하면 해당 함수의 TDD 사이클을 종료한다.

## 좋은 테스트

| 품질 | 좋음 | 나쁨 |
|---|---|---|
| **최소성** | 한 가지만 검증. 이름에 "그리고"가 들어가면 나눈다 | `testValidatesEmailAndDomainAndWhitespace` |
| **명확성** | 이름이 동작을 설명한다 | `test1` |
| **의도 표현** | 원하는 API를 보여준다 | 코드가 무엇을 해야 하는지 가린다 |

테스트를 작성하거나 변경할 때는 `references/writing-good-tests.md`를 읽고, 테스트를 정직하게 유지하는 규칙(모의객체가 아니라 실제 동작을 검증하기, 프로덕션 코드에 테스트 전용 코드를 넣지 않기, 목 대상의 부작용을 먼저 이해하기, 어떤 프로덕션 변경이 이 테스트를 실패시킬지 미리 말할 수 있는지 확인하기)을 따른다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트하겠다" | 나중에 쓴 테스트는 바로 통과한다 — 아무것도 증명하지 못한다. 잘못된 것을 검증하거나, 구현을 검증하거나, 잊어버린 경계 조건을 놓칠 수 있다. 실패하는 걸 본 적이 없으니 버그를 잡을 수 있다는 증거가 없다. |
| "테스트를 나중에 써도 목적은 같다" | 나중에 쓴 테스트는 "이게 뭘 하지?"에 답한다. 먼저 쓴 테스트는 "이게 뭘 해야 하지?"에 답한다. 나중에 쓴 테스트는 이미 짠 코드에 편향된다. |
| "이미 수동으로 테스트했다" | 수동 테스트는 임시방편이다 — 무엇을 커버했는지 기록도, 재실행 방법도 없다. 자동화된 테스트는 매번 동일하게 실행된다. |
| "X시간 들인 걸 지우는 건 낭비다" | 매몰비용의 오류다. 그 시간은 이미 썼다. 선택은 "TDD로 다시 짜기(높은 신뢰도)" 대 "그대로 두고 테스트만 붙이기(낮은 신뢰도)"뿐이다. |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 그 코드를 그대로 옮기게 된다 — 그것은 나중에 테스트하는 것이다. 삭제는 삭제다. |
| "먼저 탐색이 필요하다" | 좋다. 탐색 코드는 버리고 TDD로 다시 시작한다. |
| "테스트하기 어렵다 = 설계가 불명확하다" | 테스트의 신호를 들어라. 테스트하기 어려우면 쓰기도 어렵다. |
| "TDD는 느리게 만든다" | TDD가 오히려 실용적인 길이다 — 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 해준다. |
| "기존 코드에는 테스트가 없다" | 지금 그 코드를 개선하는 중이다. 기존 코드에도 테스트를 추가한다. |

## 위험 신호 — 멈추고 다시 시작

- 테스트보다 코드를 먼저 작성함
- 구현 후에 테스트를 작성함
- 테스트가 바로 통과함 (실패를 본 적이 없음)
- 왜 테스트가 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번만은" 이라는 합리화
- "이미 수동으로 테스트했다"
- "나중에 써도 목적은 같다"
- "참고용으로 남기겠다" 또는 "기존 코드를 그대로 옮기겠다"
- "이미 X시간을 썼으니 지우는 건 낭비다"
- "이건 다른 경우다..."

**이 중 하나라도 해당하면: 코드를 지우고 TDD로 다시 시작한다.**

## 예시: 버그 수정

**버그:** 빈 이메일이 통과됨

**RED**
```python
class TestSubmitForm(unittest.TestCase):
    def testRejectsEmptyEmail(self):
        """!
        @brief 이메일이 빈 문자열이면 오류를 반환하는지 검증한다.
        @technique 경계값분석 (빈 문자열 입력)
        @case negative
        """
        result = submitForm({"email": ""})
        self.assertEqual(result.get("error"), "Email required")
```

**RED 확인**
```
$ python -m unittest
FAIL: 'Email required' 예상, 실제 None
```

**GREEN**
```python
def submitForm(data):
    if not data.get("email", "").strip():
        return {"error": "Email required"}
    # ...
```

**GREEN 확인**
```
$ python -m unittest
OK
```

**REFACTOR**
여러 필드에 대한 검증이 필요하면 검증 로직을 추출한다.

## 완료 전 점검 체크리스트

- [ ] 새로 만든 모든 함수/메서드에 테스트가 있다
- [ ] 구현 전에 각 테스트가 실패하는 것을 직접 지켜봤다
- [ ] 각 테스트가 예상한 이유로 실패했다 (기능 없음, 오타 아님)
- [ ] 각 테스트를 통과시키는 최소한의 코드만 작성했다
- [ ] 모든 테스트가 통과한다 (CLAUDE.md 단위 테스트 지침: 테스트 성공률 100% — 실패하는 테스트를 남겨둔 채 완료로 보고하지 않는다)
- [ ] 출력이 깨끗하다 (에러/경고 없음)
- [ ] 테스트가 실제 코드를 사용한다 (모킹은 불가피한 경우만)
- [ ] 경계 조건과 오류 상황이 커버되어 있다
- [ ] 모든 테스트 함수에 Doxygen 형식(`@brief`/`@technique`/`@case`) 주석이 있다
- [ ] 도출한 테스트 케이스가 긍정/부정으로 나뉘어 있고, 부정 케이스가 0개인 함수가 없다 (설계상 예외/오류 조건이 전혀 없다고 명시적으로 확인된 경우는 예외)
- [ ] SWE.3 함수 계약의 사전조건/경계값/예외/의사결정표 행/상태전이 중 테스트로 커버되지 않은 것이 없다
- [ ] `coding` 스킬의 품질 게이트(함수 라인수/순환복잡도/중복코드/주석비율/명명/**Branch 커버리지 100%**)를 모두 통과했다
- [ ] `requirements-analyst`의 RTM(`ENG-TRC-001`)에 이 테스트를 반영했다 (해당하는 경우)

모든 항목을 체크할 수 없다면 TDD를 건너뛴 것이다. 다시 시작한다.

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 테스트 방법을 모르겠다 | 원하는 API를 먼저 적어본다. 어서션부터 쓴다. 사용자에게 물어본다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡한 것이다. 인터페이스를 단순화한다. |
| 모든 것을 모킹해야 한다 | 코드가 너무 결합되어 있다. 의존성 주입을 사용한다. |
| 테스트 준비(setup)가 방대하다 | 헬퍼를 추출한다. 그래도 복잡하면 설계를 단순화한다. |

## 디버깅과의 연결

버그를 발견했는가? 그 버그를 재현하는 실패하는 테스트를 먼저 작성한다. TDD 사이클을 따른다. 테스트가 수정을 증명하고 회귀를 방지한다.

테스트 없이 버그를 고치지 않는다.

## 최종 규칙

```
프로덕션 코드 → 테스트가 존재하고 먼저 실패했다
그렇지 않다면 → TDD가 아니다
```

사용자의 승인 없이는 예외가 없다.
