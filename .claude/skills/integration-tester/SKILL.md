# 소프트웨어 통합시험(SWE.5) 스킬

이 스킬은 `architecture-designer`(SWE.2)가 정의한 인터페이스와 통합 순서를 근거로, 구현된 소프트웨어 컴포넌트를 단계적으로 통합하며 검증하는 절차를 정의한다.

> **`sw-system-test` 스킬과의 경계**: 이 스킬은 아키텍처 인터페이스·통합순서 기반의 컴포넌트 간 상호작용 검증(코드 수준 함수/콜 커버리지 포함)만 다룬다. SW 요구사항 명세서를 베이시스로 한 블랙박스 기능/비기능 테스트 케이스는 `sw-system-test` 스킬(SWE.6 성격)의 범위이며, 여기서 다시 다루지 않는다.

## 참고자료 (필요할 때 불러오고, 통째로 대화창에 붙여넣지 말 것)

- `references/aspice-swe5-base-practices.md` — A-SPICE 4.1 SWE.5 프로세스 목적/성과/기본관행(BP1~BP7) 공식 원문 발췌. **BP2 원문이 테스트 베이시스는 아키텍처이지 상세설계 내부가 아님을 명시한다.**
- `references/iso26262-integration-test-principles.md` — ISO 26262-6 Clause 10 통합시험 방법(요구사항기반/인터페이스/결함주입/자원사용/백투백), 시험 케이스 도출 기법, **함수 커버리지·콜 커버리지**(Table 12 계열) 정의와 100% 달성 절차.
- `references/coverage-tooling.md` — `coverage.py` + `ast` 기반으로 함수 커버리지·콜 커버리지를 실제로 계산하는 Python 스크립트와 실행 절차.
- `references/swe5-template-guide.md` — 저장소 실제 템플릿(`TPL-SWE5-001` 명세서, `TPL-SWE5-002` 케이스, `TPL-SWE5-003` 결과서)의 목차/컬럼 구조와 산출물 명명 규칙.

> A-SPICE 부분은 VDA QMC 공개 프리뷰 원문 발췌이고, ISO 26262 부분은 공개 2차 자료 기반 참고 요약이다(표준 원문 직접 인용 아님). 실제 인증/심사 산출물로 확정하기 전 정식 표준 문서 대조가 필요함을 사용자에게 안내한다.

## 0. 사전 확인 (매번 수행)

1. `references/swe5-template-guide.md` 0절의 절차대로 실제 템플릿 파일을 다시 확인한다.
2. **테스트 베이시스 확보**: `architecture-designer`가 만든 `ENG-SWE2-001`(6장 인터페이스, 11장 통합 전략/순서, 7~8장 동적 동작, 4장 컴포넌트 책임)과 `ENG-SWE2-002`(drawio)의 위치를 Read/Grep/Glob으로 확인한다. 이 문서 없이 통합시험을 창작하지 않는다 — 못 찾으면 사용자에게 위치를 확인한다.
3. 구현된 소스코드(`coding` 스킬 산출물)와 그 위치, 실행 가능한 테스트 환경(unittest, `coverage.py` 설치 여부)을 확인한다.

## 1. 통합시험 절차

1. **통합 순서 확정**: `ENG-SWE2-001` 11장(통합 전략)에 정의된 통합 단위·순서·선행조건을 그대로 가져온다. 문서에 순서가 불명확하거나 코드 구현 상태와 맞지 않으면(예: 아직 구현되지 않은 컴포넌트), 임의로 순서를 바꾸지 말고 사용자에게 확인한다. 확정된 순서를 `ENG-SWE5-001` 3장(통합 항목과 순서)에 옮긴다.
2. **검증 측정치 명시 (BP1)**: 각 통합 단계에 대해 `iso26262-integration-test-principles.md` 1절의 방법(요구사항기반/인터페이스/결함주입/자원사용/백투백 — 해당하는 것만) 중 적용할 것을 정하고, 합격/불합격 기준·진입/종료 기준(함수·콜 커버리지 100% 조건 포함)·필요 인프라를 `ENG-SWE5-001` 2·4·5장에 정의한다.
3. **컴포넌트 행동 검증 측정치 명시 (BP2)**: 각 컴포넌트의 아키텍처상 선언된 행동·인터페이스(내부 구현 세부사항이 아님)를 검증할 측정치를 별도로 정의한다.
4. **시험 케이스 도출**: `ENG-SWE2-001` 6장의 인터페이스 계약(입출력, 호출조건, 시간제약, 오류계약)에 대해 동등분할/경계값분석/의사결정표/상태전이/오류추측 기법(`tdd` 스킬과 동일 어휘)을 적용해 시험 케이스를 도출한다. 각 케이스를 `ENG-SWE5-002`에 Test ID/Trace/Integration Item/Stimulus/Expected Result/Technique/Automation으로 기록한다. 근거 없는 케이스를 지어내지 않는다.
5. **선정 (BP3)**: 회귀검증 기준을 포함한 선정 기준에 따라 이번 실행 범위의 시험 케이스를 선정하고 `ENG-SWE5-001` 9장(회귀 전략)에 근거를 남긴다.
6. **통합 및 실행 (BP4/BP5)**: 확정된 순서대로 컴포넌트를 통합하며(빅뱅/지속적/단계적 중 상황에 맞는 방식 — 임의로 결정하지 말고 아키텍처·프로젝트 상황에 근거), Python `unittest`로 통합시험을 작성·실행한다. 시험 함수는 `coding` 스킬의 Doxygen 규칙에 따라 `@brief`/`@technique`(도출 기법)/`@method`(1절의 통합시험 방법)/`@case`(positive/negative)를 주석에 남긴다. 실행 결과(합격/불합격, 실제결과, 증거 위치)를 `ENG-SWE5-003`에 기록한다.
7. **커버리지 측정 및 100% 달성**: `coverage-tooling.md`의 절차로 함수 커버리지·콜 커버리지를 측정한다. 100%에 미달하면:
   - 미호출 함수/미실행 호출을 실행하는 통합시험을 추가한다 (커버리지를 위한 무의미한 호출 추가 금지 — 항상 2~4단계의 방법/기법에 근거).
   - 정말 도달 불가능한 코드라면 사용자에게 보고하고 임의로 100%를 주장하지 않는다.
   - 두 지표 모두 100%가 될 때까지 반복한다.
8. **일관성/추적성 확립 (BP6)**: 검증 측정치 ↔ 아키텍처(정적/동적)·상세설계, 검증 결과 ↔ 검증 측정치 간 양방향 추적성을 `ENG-SWE5-001` 11·13장에 확립한다. `requirements-analyst`의 RTM(`ENG-TRC-001`)의 `SWE.5`/`Coverage` 컬럼을 같은 작업 안에서 갱신한다.
9. **결과 요약 및 공유 (BP7)**: 통합시험 결과(합격/불합격 건수, 커버리지 수치, 발견된 결함, 남은 갭)를 요약해 보고한다.

## 출력 시 유의사항

- 문서(docx)/시험케이스·결과서(xlsx)는 `WP_Templates`에서 복사한 실제 템플릿 형식 그대로, `PRC-TPL-001` 등록부의 명명 규칙에 맞춰 저장한다. 저장 위치가 정해지지 않았으면 사용자에게 확인한다.
- 근거 없는 시험 케이스나 결과를 지어내지 않는다 — 반드시 아키텍처 문서와 실제 실행 결과에 근거한다.
- 함수/콜 커버리지 100% 미달 상태를 "완료"로 보고하지 않는다. 도달 불가능한 코드로 판단되는 경우를 제외하고는 반드시 100%를 달성한 뒤 완료로 보고한다.
- CLAUDE.md 통합 테스트 지침에 따라 **테스트 성공률도 100%**여야 한다 — 실패한 시험이 남아있는 상태를 완료로 보고하지 않는다. 실패가 발생하면 SUP.9 결함관리로 연결하고, 원인이 코드 결함인지 시험 케이스 오류인지 규명한 뒤 재시험한다.
- 이 스킬의 결과물은 통합시험 초안/실행 지원이며, 공식 A-SPICE 심사나 ISO 26262 인증 판정이 아님을 명시한다.
