# ISO 26262-6 기반 소프트웨어 통합시험 기법 및 구조적 커버리지 (참고 요약)

> 주의: 이 문서는 ISO 26262(2018) Part 6, Clause 10 "Software integration and verification"의 널리 알려진 개념(Table 9/10/12 계열)을 공개 2차 자료를 바탕으로 정리한 **참고용 요약**이며 표준 원문을 그대로 인용한 것이 아니다. 실제 인증 산출물로 확정하기 전에는 조직이 보유한 정식 ISO 26262-6:2018 문서로 조항·표 번호를 대조 확인할 것.

## 통합시험 방법 (Table 9 계열 개념) — "검증 측정치의 기법"(SWE.5.BP1/BP2)에 대응

| 방법 | 설명 | 이 프로젝트에서의 적용 |
|---|---|---|
| 요구사항 기반 시험 (Requirements-based test) | 소프트웨어 요구사항으로부터 도출한 시험 | 컴포넌트/인터페이스가 구현해야 할 SW 요구사항(`ENG-SWE1-001`)을 근거로 시험 케이스 도출 |
| 인터페이스 시험 (Interface test) | 컴포넌트 간 인터페이스의 데이터 형식·호출조건·시간제약 준수를 검증 | `ENG-SWE2-001` 6장의 인터페이스 계약을 그대로 시험 조건으로 사용 — 이 프로젝트의 핵심 기법 |
| 결함 주입 시험 (Fault injection test) | 의도적으로 오류/결함 조건을 주입해 오류 처리·안전 동작을 검증 | `ENG-SWE2-001` 9장(오류 격리와 안전 동작)에 정의된 오류 처리 경로 검증 |
| 자원 사용 시험 (Resource usage test) | 메모리/CPU/스택 등 자원 소비 목표 준수를 검증 | `ENG-SWE2-001` 13장(자원 및 배포 경계)의 목표치와 비교 |
| 모델-코드 백투백 시험 (Back-to-back comparison test) | 모델 기반 설계가 있는 경우 모델 실행 결과와 코드 실행 결과를 비교 | 모델 기반 설계를 사용하는 컴포넌트에만 해당 (해당 없으면 생략하고 사유를 기록) |

## 시험 케이스 도출 기법 (Table 10 계열 개념)

기법의 정의는 `../../_shared/references/test-design-techniques.md`(전 단계 공용 taxonomy, `tdd`/`sw-system-test`와 동일)를 따른다 — 여기서는 적용 대상만 규정한다. 통합시험에서는 동등분할·경계값분석·상태전이 테스트·오류추측을 **컴포넌트 인터페이스의 입출력**과 **컴포넌트 간 상호작용 시나리오**에 적용한다(컴포넌트 내부 알고리즘이 아니라). 인터페이스 파라미터 조합이 많아 전수 조합이 비현실적이면 공용 문서의 페어와이즈(PICT) 기법을 사용한다.

## 구조적 커버리지: 함수 커버리지 · 콜 커버리지 (Table 12 계열 개념) — 이 스킬의 필수 목표

소프트웨어 아키텍처(통합) 수준의 구조적 커버리지 지표는 단위 수준(문장/분기/MC-DC)과 다르다:

- **함수 커버리지(Function coverage)**: 프로그램에 존재하는 함수(서브프로그램) 중, 시험 실행 중 적어도 한 번 호출된 함수의 비율.
- **콜 커버리지(Call coverage)**: 프로그램에 존재하는 함수 호출(콜사이트) 중, 시험 실행 중 적어도 한 번 실행된 호출의 비율.
- **두 지표는 서로 다르다** — 함수 커버리지 100%가 콜 커버리지 100%를 보장하지 않는다 (같은 함수를 호출하는 여러 호출 지점 중 일부만 실행됐을 수 있음). **이 프로젝트는 두 지표를 각각 100% 달성해야 한다.**
- ASIL이 높을수록(C/D) 이 두 지표가 강하게 권고되지만, 이 스킬은 ASIL과 무관하게 항상 100%를 목표로 한다 (사용자가 명시적으로 완화를 요청하지 않는 한).
- 측정 방법(Python 프로젝트에는 두 지표를 직접 산출하는 상용 임베디드 커버리지 툴이 아니라, 오픈소스 `coverage.py` + 정적분석으로 산출한다)은 `coverage-tooling.md`를 참고한다.
- 커버리지가 100%에 못 미치는 함수/호출이 남으면:
  1. 해당 함수/호출을 실행하는 통합시험 케이스를 추가한다 (1절의 방법·기법을 사용).
  2. 정말로 도달 불가능한 코드(죽은 코드, 비활성 코드, 방어적 코드 등)라고 판단되면, 임의로 무시하지 말고 사용자에게 보고한다 — 코드 제거/설계 확인이 필요할 수 있다.
  3. 100%를 인위적으로 맞추기 위해 무의미한 호출만 추가하는 것(커버리지를 위한 커버리지)을 하지 않는다 — 항상 실제 통합 시나리오(1절의 방법)에 근거한 시험이어야 한다.

## SWE.4(단위검증)와의 경계

이 스킬은 컴포넌트 간 상호작용과 컴포넌트의 아키텍처 수준 행동을 검증하는 것이지, 컴포넌트 내부 함수의 상세 로직(사전조건/사후조건/알고리즘 분기 등)을 재검증하는 것이 아니다 — 그것은 이미 `coding`/`tdd` 스킬이 SWE.4 관점에서 단위 수준으로 다룬다. 다만 통합시험 실행 중 자연스럽게 호출되는 내부 함수의 커버리지도 함수/콜 커버리지 집계에는 포함된다(중복 검증을 피하되, 커버리지 집계 자체는 배제하지 않는다).
