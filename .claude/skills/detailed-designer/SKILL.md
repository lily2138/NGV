# 상세설계(SWE.3) 스킬

이 스킬은 소프트웨어 아키텍처(SWE.2)의 컴포넌트를 구현 가능한 소프트웨어 단위(함수/모듈)로 분해하고, 그 정적/동적 설계를 명세하는 절차를 정의한다.

## 참고자료 (필요할 때 불러오고, 통째로 대화창에 붙여넣지 말 것)

- `references/aspice-swe3-base-practices.md` — A-SPICE 4.1 SWE.3(소프트웨어 상세설계 및 단위 구현) 프로세스 목적/성과/기본관행(BP1~BP5) 공식 원문 발췌.
- `references/iso26262-unit-design-principles.md` — ISO 26262-6 Clause 8(단위 설계/구현) 코딩 가이드라인 주제, 단위 설계 원칙(단일 진입/종료점, 포인터/재귀/전역변수 제한 등), 단위 설계 검증 방법 참고 요약.
- `references/unit-design-quality.md` — 함수 계약(Design by Contract) 작성법, 복잡도 관리, 정책 의사결정표 작성법, 상태전이 상세 작성법, **SWE.2 인터페이스 불변 원칙**, 추적성/명확성 규칙.
- `references/swe3-template-guide.md` — 저장소 실제 템플릿(`TPL-SWE3-001.docx`, `TPL-SWE3-002.drawio`, 선택적으로 `TPL-SBOM-001.xlsx`)의 목차/도형 구조와 산출물 명명 규칙.

> A-SPICE 부분은 VDA QMC 공개 프리뷰 원문 발췌이고, ISO 26262 부분은 공개 2차 자료 기반 참고 요약이다(표준 원문 직접 인용 아님). 실제 인증/심사 산출물로 확정하기 전 정식 표준 문서 대조가 필요함을 사용자에게 안내한다.

## 0. 사전 확인 (매번 수행)

1. `references/swe3-template-guide.md` 0절의 절차대로 실제 템플릿 파일을 다시 확인한다. **TPL-SWE3-001은 승인 버전이 v0.9(초안)이므로 최신 버전 여부를 사용자에게 확인**한다.
2. 입력이 되는 SWE.2 아키텍처 산출물(`ENG-SWE2-001`/`002`)과 SWE.1 요구사항(`ENG-SWE1-001` 등), RTM(`ENG-TRC-001`)의 위치를 Read/Grep/Glob으로 확인한다. 아키텍처/요구사항 없이 상세설계를 창작하지 않는다 — 못 찾으면 사용자에게 위치를 확인한다.
3. 상세설계 대상 컴포넌트(SWE.2에서 정의된 어떤 컴포넌트를 상세화할지)를 확인한다. 여러 컴포넌트를 한 번에 요청받으면, 각 컴포넌트별로 아래 절차를 반복한다.

## 1. 상세설계 절차

1. **인터페이스 확인**: 대상 컴포넌트가 SWE.2에서 정의한 외부 인터페이스(제공/요구 인터페이스)를 먼저 확인한다. 상세설계 과정에서 이 인터페이스를 변경해야 할 필요가 발견되면, 임의로 변경하지 말고 즉시 작업을 멈추고 아키텍처 변경 필요성을 사용자에게 보고한다 (`unit-design-quality.md` 5절 "인터페이스 불변 원칙").
2. **모듈 분해**: 컴포넌트를 구현 단위(함수/클래스/모듈)로 분해하고 각 단위의 ID·책임·소스 위치를 정의한다 (템플릿 2장). 단위 하나에 서로 다른 이유로 바뀌는 책임이 섞여 있지 않은지 점검한다.
3. **정적 설계**: 공통 자료형(4장)과 핵심 함수 계약(5장)을 `unit-design-quality.md` 1절 형식으로 작성한다. 사전조건/사후조건/부작용/예외/시간제약을 빠짐없이 명시하고, 모호어를 사용하지 않는다.
4. **동적 설계**: 호출관계(3장, TPL-SWE3-002 drawio와 함께)와 핵심 알고리즘(6장)을 작성한다. 판단조건과 경계값을 명시적으로 나열한다 (`unit-design-quality.md` 2절).
5. **결정 로직/상태**: 조건 조합에 따라 동작이 달라지는 로직은 정책 의사결정표(7장)로, 상태 기반 동작은 상태전이 상세(8장)로 작성한다 (`unit-design-quality.md` 3~4절). 상충되는 규칙이나 정의되지 않은 상태×이벤트 조합이 없는지 점검한다.
6. **오류/방어 동작**: 유효하지 않은 입력, 예외, 자원 실패에 대한 검출·처리·기록·복구를 10장에 작성한다. ISO 26262-6 코딩 원칙(`iso26262-unit-design-principles.md`)의 방어적 구현 개념을 반영한다.
7. **코딩/검증 규칙**: 11장에 코딩 표준(프로젝트가 채택한 것이 있으면 그것을, 없으면 사용자에게 확인), 정적분석·단위검증·커버리지·리뷰 기준을 명시한다. 실제 수행 가능한 검증 방법만 제시한다 (`iso26262-unit-design-principles.md` "단위 설계 검증 방법" 참고).
8. **구현 경계**: 생성 코드, 외부 라이브러리, 플랫폼 종속부, 구현하지 않는 범위를 13장에 명시한다. 오픈소스/서드파티 의존성이 있으면 `TPL-SBOM-001` 등록을 안내한다.
9. **추적성/일관성**: 12장·14장에서 이 상세설계 요소들을 SWE.2 아키텍처 요소, SW 요구사항, (아직 없다면 예정된) 단위시험과 연결한다. `requirements-analyst`가 관리하는 RTM(`ENG-TRC-001`)의 `Detailed Design`/`Code` 컬럼을 같은 작업 안에서 갱신한다. 고아 설계(상위 매핑 없음)나 설계에 반영되지 않은 요구사항(누락)을 발견하면 갭으로 보고한다.
10. **명확성/일관성 자체 점검**: `unit-design-quality.md` 6절 기준으로 함수 계약·자료형·API 명세의 모호어를 점검하고, 인접 단위/컴포넌트의 기존 설계와 용어·단위·조건이 상충하지 않는지 확인한다. 상충 발견 시 임의로 하나를 택하지 말고 사용자에게 알린다.
11. **결과 보고**: 템플릿 형식에 맞춘 상세설계서(및 drawio, RTM 갱신분)를 제시하고, 컴포넌트/단위별로 (a) 인터페이스 불변 여부, (b) 함수 계약 완결성, (c) 추적 상태, (d) 남은 이슈/확인 필요 사항을 요약해 보고한다.

## 출력 시 유의사항

- 문서(docx)/다이어그램(drawio)/RTM(xlsx)은 `WP_Templates`에서 복사한 실제 템플릿 형식 그대로, `PRC-TPL-001` 등록부의 명명 규칙에 맞춰 저장한다. 저장 위치가 정해지지 않았으면 사용자에게 확인한다.
- 산출물을 지어내지 않는다 — 입력 아키텍처/요구사항 근거가 없는 설계 요소를 만들지 말고, 불확실한 부분은 질문하거나 "확인 필요"로 표시한다.
- 이 스킬의 결과물은 초안/설계 지원이며, 공식 A-SPICE 심사나 ISO 26262 인증 판정이 아님을 명시한다.
