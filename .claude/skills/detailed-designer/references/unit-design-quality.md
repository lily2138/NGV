# 상세설계 품질 확보 방안 (계약 기반 설계, 복잡도, 추적성)

## 1. 함수 계약(Design by Contract) — 템플릿 5장 "핵심 함수 계약"

모든 핵심 함수는 다음을 빠짐없이 명시한다. 항목이 "없음"이면 명시적으로 "없음"이라고 쓴다(생략하지 않는다 — 생략은 누락인지 의도적 없음인지 구분되지 않아 추적성/검증성을 해친다).

| 항목 | 설명 |
|---|---|
| 사전조건(Precondition) | 호출 전 성립해야 하는 입력/상태 조건 |
| 사후조건(Postcondition) | 정상 반환 시 보장되는 출력/상태 |
| 불변조건(Invariant) | 함수 실행 전후로 유지되어야 하는 조건 |
| 부작용(Side effect) | 전역 상태, 출력 파라미터, 하드웨어 레지스터 등에 대한 변경 |
| 예외/오류 처리 | 사전조건 위반, 자원 실패 시의 동작 (오류 코드 반환, 방어적 기본값 등 — 임의 동작 금지) |
| 시간 제약 | 최대 실행시간, 주기, 데드라인(해당하는 경우) |

이 계약은 그대로 SWE.4(단위검증) 테스트 케이스의 입력 동등분할/경계값/오류주입 시나리오의 근거가 된다 — 계약이 모호하면 이후 단위시험을 설계할 수 없으므로, `iso26262-requirement-quality.md`(requirements-analyst 스킬)의 명확성 기준(모호어 금지, 정량적 조건)을 함수 계약에도 동일하게 적용한다.

## 2. 복잡도 관리 — 템플릿 6장 "핵심 알고리즘"

- 함수당 순환복잡도(cyclomatic complexity)가 높아지면(대략 10~15 이상) 분해를 검토한다 — 구체적 임계값은 프로젝트 코딩 표준을 따르며, 표준이 없으면 사용자에게 채택 기준을 확인한다(임의로 숫자를 단정하지 않는다).
- 알고리즘은 의사코드 또는 흐름도로 표현하고, 판단조건과 경계값(boundary value)을 명시적으로 나열한다 — 경계값 목록은 SWE.4 경계값 분석 테스트케이스의 입력이 된다.
- 알고리즘 설명에 EARS류 문장 패턴(WHEN/WHILE/IF)을 사용해 조건-동작 대응을 명확히 한다.

## 3. 정책 의사결정표 — 템플릿 7장

여러 입력 조건의 조합에 따라 동작이 달라지는 로직은 자연어 서술 대신 **의사결정표(decision table)**로 작성한다.

- 모든 입력 조건의 조합(가능하면 전체 조합, 조합이 많으면 동등한 조합을 그룹화한 근거를 명시)을 행으로 나열한다.
- 각 행에 대해 기대 동작과 우선순위를 명시한다.
- 서로 다른 행이 동일 조건에서 상충하는 기대 동작을 갖지 않는지(일관성) 점검한다 — 상충 발견 시 사용자에게 확인한다.
- 이 표는 그대로 SWE.4의 결정 테이블 기반 테스트케이스 생성 근거가 된다.

## 4. 상태전이 상세 — 템플릿 8장

- 상태 저장 위치(변수/메모리), 전이 함수, 이벤트, 가드 조건, 타이머, 초기화 동작을 모두 명시한다.
- 정의되지 않은 상태×이벤트 조합(금지 전이)이 발생했을 때의 동작(무시/오류/안전상태 전이)을 반드시 명시한다 — SWE.2 아키텍처의 8장(상태 전이, 상위 수준)과 일관되어야 한다.

## 5. 일관성/추적성 규칙 (필수)

- **인터페이스 불변 원칙**: 상세설계는 SWE.2에서 정의된 컴포넌트 외부 인터페이스를 변경하지 않는다. 상세설계 중 인터페이스 변경이 필요하다고 판단되면, 임의로 진행하지 말고 아키텍처 변경 필요성을 사용자에게 보고하고 멈춘다 (`architecture-designer`의 "인터페이스 전용 통신" 원칙과 정합).
- 상세설계 요소는 반드시 상위 아키텍처 요소(컴포넌트)와 소프트웨어 요구사항 양쪽에 매핑되어야 한다 (템플릿 12장). 매핑되지 않는 상세설계 요소(고아 설계)나, 설계에 반영되지 않은 요구사항(누락)이 있으면 갭으로 보고한다.
- 소스 파일/함수 단위까지 추적성을 확장할 때(템플릿 14장), `requirements-analyst`가 관리하는 RTM(`TPL-TRC-001` → `ENG-TRC-001`)의 `Detailed Design`/`Code` 컬럼을 같은 작업 안에서 갱신한다 (나중으로 미루지 않는다).
- 외부 라이브러리/생성 코드/플랫폼 종속부(템플릿 13장 "구현 경계")는 이 프로세스의 상세설계 대상이 아니지만, 사용 여부와 경계는 명시해야 한다. 오픈소스/서드파티 의존성을 도입하는 경우, 해당 정보가 라이선스 관리 대상이면 `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록 템플릿.xlsx`(→ `ENG-SBOM-001_...xlsx`, Package/Version/Dependency Type/SPDX/Evidence Type/Evidence Locator/Distribution/Remark 컬럼)에 등록하도록 안내한다.

## 6. 명확성 (함수/자료형 명세에도 동일 원칙 적용)

`requirements-analyst` 스킬의 `iso26262-requirement-quality.md`에 정의된 모호어 금지 목록과 6대 품질속성(명확함/이해가능/원자적/일관됨/실현가능/검증가능)을 함수 계약, 자료형 정의(템플릿 4장), API 상세(템플릿 9장)에도 동일하게 적용한다. 예: "적절히 처리한다" (X) → "입력값이 범위를 벗어나면 오류 코드 `E_RANGE`를 반환하고 출력을 변경하지 않는다" (O).
