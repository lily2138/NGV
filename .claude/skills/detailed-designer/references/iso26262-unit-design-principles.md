# ISO 26262-6 기반 소프트웨어 단위 설계/구현 원칙 (참고 요약)

> 주의: 이 문서는 ISO 26262(2018) Part 6, Clause 8 "Software unit design and implementation"의 널리 알려진 개념(Table 1/5/6 계열)을 공개 2차 자료를 바탕으로 정리한 **참고용 요약**이며 표준 원문을 그대로 인용한 것이 아니다. A-SPICE SWE.3.BP3 원문이 직접 "ISO 26262-6 Clause 8.4.5 및 Table 6 참고"를 지시하므로, 실제 인증 산출물로 확정하기 전에는 조직이 보유한 정식 ISO 26262-6:2018 문서로 조항·표 번호를 반드시 대조 확인할 것.

## 단위 설계/구현의 목적 (Clause 8 개념)
- 상세설계와 일치하는, 요구사항을 만족하는 소프트웨어 단위를 구현한다.
- 코드가 이해하기 쉽고(readable), 검증 가능하며(verifiable), 유지보수 가능하도록(maintainable) 만드는 코딩 원칙/가이드라인을 적용한다.
- 해당 ASIL에 맞는 방법으로 단위 설계를 검증한다 (→ SWE.4 단위검증으로 이어짐).

## 모델링/코딩 가이드라인이 다루어야 할 주제 (Table 1 계열 개념)

아래 주제들을 조직/프로젝트의 코딩 표준(예: MISRA C 등 언어 서브셋)이 다루고 있는지 확인하고, 다루지 않는 항목이 있으면 템플릿 11장(코딩 및 검증 규칙)에 프로젝트 차원의 보완 규칙을 명시한다.

- 낮은 복잡도 강제 (순환복잡도 등 정량 기준)
- 언어 서브셋 사용 (안전하지 않은 언어 기능 배제)
- 강한 타입 검사 강제, 암묵적 형변환 금지
- 명명 규칙 준수
- 낮은 결합도 강제(단위 간)
- 방어적 구현(defensive implementation) — 입력 범위 검사 등
- 오류 처리 관례의 일관성
- 최소화된 공유 자원 사용 (전역변수 등)
- 동시성(concurrency) 측면 고려

## 단위 설계 원칙 (Table 5 계열 개념)

| 원칙 | 설명 |
|---|---|
| 단일 진입점·단일 종료점 | 서브루틴(함수)은 하나의 진입점과 하나의 종료점만 가진다 |
| 제한된 포인터 사용 | 포인터 산술/다중 간접참조를 최소화한다 |
| 동적 객체/변수 미사용 (또는 생성 시 온라인 시험) | 런타임 동적 메모리 할당을 피하거나, 불가피하면 생성 시점에 온라인 검사를 수행한다 |
| 제한된 재귀 사용 | 재귀 깊이가 정적으로 한정되지 않으면 스택 오버플로 위험 — 재귀 사용을 제한하거나 반복문으로 대체 |
| 무조건 분기(goto) 지양 | 제어흐름을 예측 가능하게 유지 |
| 낮은 순환복잡도 | 함수당 분기 경로 수를 제한해 이해·검증 용이성 확보 (MC/DC 커버리지 확보에도 유리 — SWE.4 연계) |
| 모든 변수 초기화 | 사용 전 모든 변수를 초기화 |
| 변수/식별자 이름 재사용 금지 | 스코프가 다르더라도 동일 이름 재사용으로 인한 혼동을 방지 |
| 전역변수 사용 제한 | 부득이한 경우 접근을 통제하고 문서화 (A-SPICE의 "공유자원 관리" 원칙과 연결) |
| 인터럽트 사용 제한 | 필요한 경우로 한정하고 우선순위/재진입성을 명시 |

> CL1 수준 코딩 원칙 예시(암묵적 형변환 금지, 단일 진입/종료점, 범위 검사)는 A-SPICE SWE.3.BP3 원문에도 직접 언급되어 있다 (`aspice-swe3-base-practices.md` 참고).

## 단위 설계 검증 방법 (Table 6 계열 개념)

템플릿 11장(코딩 및 검증 규칙)·6장(핵심 함수 계약) 작성 시, 실제 수행 가능한 방법을 명시한다 (수행 불가능한 방법을 나열하지 않는다 — `requirements-analyst`/`architecture-designer` 스킬과 동일한 "실행 가능성" 원칙 적용):

- 워크스루(walk-through), 인스펙션(inspection) — 리뷰 기반
- 정적분석(static code analysis) — 코딩 표준 위반, 널 포인터, 미초기화 변수 등 검출
- 제어흐름분석(control flow analysis) — 도달 불가 코드, 무한루프 등
- 데이터흐름분석(data flow analysis) — 미정의 변수 사용, 데드 스토어 등
- 정형검증/기호실행(formal verification / symbolic execution) — 높은 ASIL에서 강하게 권고

## MISRA C 등 언어 서브셋과의 관계
C/C++ 사용 시, 위 원칙의 상당 부분은 MISRA C(또는 해당 언어의 동등한 서브셋 표준) 준수로 커버된다. 프로젝트가 MISRA 등 특정 코딩 표준을 채택했다면, 템플릿 11장에는 그 표준명/버전과 편차(deviation) 관리 절차를 기록하고 이 문서의 원칙을 별도로 재나열하지 않는다.

## SWE.2(아키텍처)와의 경계
- 컴포넌트 간 인터페이스는 SWE.2에서 이미 확정된 것이며, SWE.3은 그 인터페이스를 변경하지 않고 컴포넌트 **내부** 단위로 분해·구현한다.
- 상세설계 중 기존 인터페이스로 요구사항을 만족시킬 수 없다고 판단되면, 임의로 인터페이스를 새로 만들지 말고 아키텍처 변경 필요성을 사용자에게 보고한다.
