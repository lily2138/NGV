# A-SPICE 4.1 SWE.3 (소프트웨어 상세설계 및 단위 구현) 공식 원문 발췌

> 출처: VDA QMC "Automotive SPICE PAM 4.1" (공개 프리뷰), 4.4.3절. `architecture-designer` 스킬의 `aspice-swe2-base-practices.md`와 이어지는 다음 프로세스이다.

## 프로세스 목적
정적/동적 측면을 모두 포함하며 소프트웨어 아키텍처와 일치하는 소프트웨어 상세설계를 수립하고, 그 상세설계와 일치하는 소프트웨어 단위(software unit)를 구현하는 것.

## 프로세스 성과(outcome)
1. 정적/동적 측면을 포함한 상세설계가 명시된다.
2. 상세설계에 명시된 대로 소프트웨어 단위가 구현된다.
3. 상세설계와 소프트웨어 아키텍처 사이에 일관성과 양방향 추적성이 확립된다.
4. 소스코드와 상세설계 사이에 일관성과 양방향 추적성이 확립된다.
5. 상세설계와 소프트웨어 요구사항 사이에 일관성과 양방향 추적성이 확립된다.
6. 소스코드와 합의된 상세설계가 관련된 모든 당사자에게 전달(공유)된다.

## 기본관행(Base Practices)

**SWE.3.BP1 — 상세설계의 정적 측면을 명시한다.** 각 소프트웨어 컴포넌트에 대해, 그 소프트웨어 단위들의 행동, 정적 구조와 관계, 그리고 인터페이스(입출력의 유효 데이터 값 범위·응용도메인 관점의 물리/측정 단위 포함)를 명시한다.
- 참고: 소프트웨어 단위의 경계는 소스코드/파일 구조/모델 기반 구현상의 표현과 무관하며, 응용도메인 관점의 의미(semantics)로 정해진다. 따라서 하나의 단위가 코드 수준에서 하나 또는 여러 서브루틴으로 표현될 수 있다.
- 참고: 유효 데이터 값 범위의 예 — `0..200 [m/s]`, `0..3.8 [A]`, `1..100 [N]`. 이런 응용도메인 값 범위를 프로그래밍 언어 수준 자료형(예: 0..65535 범위의 unsigned Integer)으로 매핑하는 것은 BP2에서 다룬다.
- 참고: 측정 단위의 예 — `%`. 카운터처럼 물리/측정 단위가 적용되지 않는 파라미터/반환값도 있다.
- 참고: HSI(하드웨어-소프트웨어 인터페이스) 정의는 시스템 설계(SYS.3)의 영역이다.

**SWE.3.BP2 — 상세설계의 동적 측면을 명시한다.** 소프트웨어 아키텍처와 관련하여, 컴포넌트의 동적 행동을 완수하기 위한 관련 소프트웨어 단위들 간의 상호작용을 포함해 동적 측면을 명시·문서화한다.
- 참고: 행동 서술의 예 — 자연어 또는 준형식(semi-formal) 표기법(예: SysML, UML).

**SWE.3.BP3 — 소프트웨어 단위를 개발한다.** 상세설계와 일치하고, 코딩 원칙(coding principles)에 따라 소프트웨어 단위를 개발·문서화한다.
- 참고: CL1 수준의 코딩 원칙 예 — 암묵적 형변환 미사용, 서브루틴의 단일 진입점·단일 종료점, 범위 검사(설계 계약(design-by-contract), 방어적 프로그래밍). **추가 예시는 ISO 26262-6 Clause 8.4.5와 Table 6을 참고한다** (A-SPICE 원문이 직접 지시하는 상호참조).

**SWE.3.BP4 — 일관성을 확보하고 양방향 추적성을 확립한다.** 다음 세 쌍 사이에 일관성을 확보하고 양방향 추적성을 확립한다: ① 상세설계 ↔ 소프트웨어 아키텍처, ② 개발된 소프트웨어 단위 ↔ 상세설계, ③ 상세설계 ↔ 소프트웨어 요구사항.
- 참고: 여러 추적 접근 방식을 혼용해 중복이 생기지 않도록 한다.
- 참고: 소프트웨어 단위를 요구사항에 직접 추적하는 예 — 통신 매트릭스, 또는 AUTOSAR 설정에 내재된 진단 식별자 목록과 같은 기본 소프트웨어(BSW) 측면.
- 참고: 양방향 추적성은 일관성을 뒷받침하고 변경영향분석·커버리지 입증을 용이하게 한다. 링크의 존재 자체가 정보의 일관성을 보장하지는 않는다.

**SWE.3.BP5 — 합의된 상세설계와 개발된 소프트웨어 단위를 전달(공유)한다.** 관련된 모든 당사자에게 전달한다.

## 이 스킬에 대한 시사점

- BP1(정적)·BP2(동적) — 템플릿 2~9장(모듈 분해, 호출관계, 자료형, 함수 계약, 알고리즘, 정책표, 상태전이, API 상세)에 대응.
- BP3의 "코딩 원칙" — `iso26262-unit-design-principles.md`(ISO 26262-6 Clause 8 참고 요약)를 적용해 템플릿 11장(코딩 및 검증 규칙)에 반영한다.
- BP4의 세 방향 일관성/추적성 — 템플릿 12장(단위와 요구사항 할당)·14장(추적성)에서 확보하며, `architecture-designer`가 만든 SWE.2 산출물, `requirements-analyst`가 관리하는 RTM(TPL-TRC-001)과 연동한다. **상세설계는 SWE.2에서 정의한 컴포넌트 인터페이스를 변경하지 않는다** — 인터페이스 변경이 필요하면 상세설계를 멈추고 아키텍처 변경(architecture-designer 재작업)을 먼저 요청한다.
- BP5 — 산출물 작성 후 리뷰/승인(템플릿 "작성 검토 승인 상태" 표)과 공유 증적을 남긴다.
